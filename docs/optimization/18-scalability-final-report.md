# 최종 보고서: 서비스 확장성 한계 측정 및 돌파

> 작성일: 2026-03-17
> 환경: GCP e2-standard-2 (2 vCPU, 8GB), MySQL 8.0 Docker, Redis 7
> 데이터: 10,000 회원, 184,000 게시글, 6.2M 좋아요, 538,000 팔로우

---

## 1. 프로젝트 목표

SNS 다이어리 서비스(CoreDisc)의 **확장성 한계를 측정하고 돌파**하는 것.

1. **Part A (동시성)**: 좋아요 카운트 정합성 문제를 발견하고 해결
2. **Part B (피드 확장성)**: 팔로잉 수 증가에 따른 피드 성능 저하를 개선
3. **통합 검증**: 실제 서비스 워크로드에서 최종 한계점 도출

## 4. 최종 한계점 도출

### 4-1. 서비스 안정 한계

```
이 서비스는 e2-standard-2 (2 vCPU, 8GB) 단일 서버에서:

✅ 동시 접속 200명까지: p95 < 2s, 에러 0%, 정합성 100%
✅ 동시 접속 500명까지: p95 < 5.2s, 에러 0%, 처리량 96 req/s
⚠️ 동시 접속 500명 초과: HikariCP pool=50 포화 → 커넥션 대기 증가

예상 MAU 환산 (동시접속률 5% 가정):
  200명 동시 → MAU ~4,000명
  500명 동시 → MAU ~10,000명
```

### 4-2. 다음 병목 지점

현재 서버 사양 (e2-standard-2)에서의 병목:

| 순위 | 병목 지점 | 현상 | 해결 방안 |
|------|----------|------|----------|
| 1 | DB 커넥션 풀 (HikariCP 50) | 500 VU 시 커넥션 대기 발생 | 서버 스케일업 또는 Read Replica |
| 2 | CPU (2 vCPU) | 500 VU 시 CPU 포화 | e2-standard-4로 업그레이드 |
| 3 | Redis 단일 노드 | 대규모 캐시 요청 시 | Redis Cluster 도입 |

### 4-3. 확장 전략 (도입 순서)

```
1단계: 서버 스케일업 (e2-standard-4, pool=100)
   → 예상: 동시 1,000명, MAU ~20,000명

2단계: Read Replica 분리
   → 읽기 쿼리를 Replica로, 쓰기만 Master
   → 예상: 동시 2,000명, MAU ~40,000명

3단계: Pull/Push 하이브리드 피드
   → Redis Sorted Set 타임라인 캐시 + 선택적 fan-out
   → 예상: 동시 10,000명+, MAU ~200,000명
```

## 5. 의사결정 근거 정리

### SKIP한 최적화와 그 근거

| 계획 | 결정 | 근거 |
|------|------|------|
| 3가지 락 전략 비교 (Phase 2-4) | **SKIP** | DB 원자적 연산 Row Lock avg=54ms로 충분 |
| Redis 카운터 (Phase 2-5) | **SKIP** | 동시 200건까지 에러 0%, 현실적 규모에서 불필요 |
| Caffeine 튜닝 (Phase 3-3) | **SKIP** | HIT율 83-99%, maxSize 활용률 9%, 튜닝 여지 없음 |
| Pull/Push 하이브리드 (Phase 3-5) | **SKIP** | FORCE INDEX 최적화로 p95 70-83% 감소, 현재 규모 충분 |

### 핵심 기술 선택과 그 이유

| 기술 선택 | 이유 |
|----------|------|
| DB 원자적 연산 (vs 비관적/낙관적 락) | 가장 단순하고 InnoDB 원자성 보장, Row Lock avg 54ms |
| FORCE INDEX(PRIMARY) 역순 스캔 | EXPLAIN ANALYZE 기반 발견, 팔로잉 수 역전 패턴 활용 |
| 비동기 이벤트 (AFTER_COMMIT + REQUIRES_NEW) | 카운트 실패가 좋아요 생성에 영향 없도록 격리 |
| Redis 피드 캐시 (TTL 30s + 분산 락) | Thundering Herd 방어, 첫 페이지 캐시로 DB 부하 감소 |

## 8. 면접 예상 질답

### Q1. 동시성 문제를 어떻게 발견했나요?
> 좋아요 카운트 증가 로직이 없는 것을 발견하고, JPA Dirty Checking으로 구현했더니 k6 동시성 테스트에서 Deadlock 78%, Lost Update 91건이 발생했습니다. JPA의 `SELECT → 수정 → UPDATE` 흐름이 InnoDB Row Lock 충돌을 일으킨 것이었습니다.

### Q2. 왜 Redis 카운터 대신 DB 원자적 연산을 선택했나요?
> 동시 200건 좋아요 테스트에서 에러 0%, 정합성 100%를 확인했습니다. SNS 다이어리 앱에서 같은 글에 동시 200명이 좋아요를 누르는 상황은 현실적으로 극히 드뭅니다. Redis 카운터는 동기화 배치, Eventual Consistency, 장애 폴백 등 복잡도를 추가하는데, 측정 결과 DB 원자적 연산으로 충분했습니다. "DB로 충분한데 왜 Redis를 쓰는가?"를 데이터로 증명한 것입니다.

### Q3. FORCE INDEX(PRIMARY) 최적화를 어떻게 발견했나요?
> EXPLAIN ANALYZE로 피드 쿼리 실행 계획을 분석했더니, MySQL이 `idx_post_member_status` 인덱스를 선택하여 팔로잉한 유저의 모든 게시글을 스캔한 후 정렬하고 있었습니다. 팔로잉 5000명이면 61,542행을 스캔하여 11행만 반환하는 비효율이었습니다.
>
> PRIMARY KEY 역순 스캔을 시도하면, MySQL이 가장 최신 게시글부터 역순으로 스캔하면서 `member_id IN (...)` 조건을 검사합니다. 팔로잉 5000명이면 최근 게시글의 50%가 팔로잉한 사람의 글이므로, 53행만 스캔하면 11행을 찾을 수 있습니다.

### Q4. 이 최적화의 한계는 무엇인가요?
> 두 가지 한계가 있습니다.
> 1. **팔로잉이 매우 적은 경우**: 팔로잉 10명 미만이면 역순 스캔으로도 많은 행을 읽어야 합니다. 이 경우 기존 인덱스 스캔이 더 효율적일 수 있습니다.
> 2. **오래된 게시글 조회 (deep pagination)**: 커서가 매우 오래된 게시글 ID를 가리키면, 그 지점까지 역순 스캔해야 합니다. 다만 실사용에서는 대부분 최신 피드를 조회하므로 실질적 영향은 적습니다.
>
> 이 한계를 넘으려면 Pull/Push 하이브리드 아키텍처 (Redis Sorted Set 타임라인) 도입이 필요합니다.

### Q5. 측정 없이 Redis를 먼저 도입했다면 어떤 문제가 있었을까요?
> "Redis가 필요할 것이다"라는 가정 없이 측정부터 시작한 것이 핵심입니다. 실제로 측정해보니 DB 원자적 연산으로 동시성은 충분했고, FORCE INDEX 최적화로 피드 성능도 크게 개선되었습니다. Redis를 먼저 도입했다면 불필요한 복잡도(캐시 동기화, Eventual Consistency, 장애 폴백)를 추가했을 것이고, 진짜 병목인 쿼리 실행 계획 문제는 발견하지 못했을 것입니다.
