# Phase 1 + Phase 2 종합: 확장성 한계 측정 및 동시성 해결

> 작성일: 2026-03-16
> 환경: GCP e2-standard-2, MySQL 8.0, Redis 7, HikariCP pool=50

---

## 1. 측정 결과 종합

### 1-1. Part A: 동시성 (좋아요 카운트 정합성)

#### 가설 검증

| 가설 | 결과 | 판정 |
|------|------|------|
| "JPA Dirty Checking 기반 카운트 증가는 동시 요청 시 Lost Update 발생" | 동시 50건에서 Deadlock 78%, Lost Update 91건 | **지지** |
| "동시성이 높을수록 유실률 증가" | 50건에서 이미 치명적 수준 | **지지** |
| "DB 원자적 연산으로 유실률 0%" | 100VU, 200VU 모두 diff=0 | **지지** |

#### Before/After

| 지표 | Before (JPA Dirty Checking) | After (DB 원자적 연산) |
|------|---------------------------|---------------------|
| Deadlock | 78% | **0%** |
| Lost Update | 91건 괴리 | **0건 (diff=0)** |
| 에러율 (100 VU) | 높음 | **0%** |
| 에러율 (200 VU) | N/A | **0%** |
| 에러율 (500 VU) | N/A | 23.4% (서버 용량 한계) |
| Row Lock avg | N/A (Deadlock) | **54~59ms** |

#### 스케일 한계

- **200 VU까지**: 에러 0%, 정합성 100% → 서비스 안정
- **500 VU**: 서버 과부하로 에러 발생, 비동기 이벤트 유실
- **결론**: DB 원자적 연산은 현실적 서비스 규모에서 충분

### 1-2. Part B: 피드 확장성 (팔로잉 수별 성능)

#### 가설 검증

| 가설 | 결과 | 판정 |
|------|------|------|
| "팔로잉 수 증가 시 응답 시간 선형 이상 증가" | median은 차이 미미, p95에서 점진적 증가 | **부분 지지** |
| "팔로잉 500명 이상에서 p95 > 1초" | 50명에서 이미 p95 5.49s | **기각** (이미 초과) |
| "VU 증가 시 DB 커넥션 풀이 병목" | 500 VU에서 에러 0.19% | **약한 지지** |

#### 팔로잉 수별 피드 응답 시간 (90 VUs)

| 팔로잉 수 | avg | median | p95 |
|-----------|-----|--------|-----|
| 50 | 1.03s | 97ms | 5.49s |
| 200 | 1.01s | 157ms | 5.55s |
| 500 | 1.06s | 84ms | 6.68s |
| 1000 | 1.02s | 112ms | 7.03s |
| 2000 | 1.17s | 52ms | 9.57s |
| 5000 | 1.17s | 46ms | 9.67s |

**핵심 발견**:
- **median(50%)은 팔로잉 수에 거의 무관** (46ms ~ 157ms)
- **p95는 팔로잉 수 증가에 따라 점진적 증가** (5.49s → 9.67s)
- **전체 에러율 0%** — 팔로잉 5000명에서도 요청 실패 없음

#### VU 단계적 증가 (50→500 VU ramp)

| 지표 | 결과 |
|------|------|
| avg | 1.97s |
| median | 148ms |
| p95 | 16.35s |
| 에러율 | 0.19% |
| 처리량 | 64.1 req/s |

## 2. Phase 2, 3 방향 결정

### Part A: 동시성 → **Phase 2 완료**

- DB 원자적 연산으로 문제 해결 완료
- Redis 카운터 불필요 (200 VU까지 에러 0%)
- 락 전략 비교 불필요 (원자적 UPDATE가 최선)

### Part B: 피드 확장성 → **Phase 3에서 해결**

**관찰된 패턴:**
- median이 양호한 것 = 대부분의 요청은 빠르게 처리
- p95가 높은 것 = 일부 요청이 DB 커넥션 풀/쿼리 경합에서 지연
- 팔로잉 수보다 **동시 요청 수(VU)**가 더 큰 영향

**Phase 3 접근:**
1. EXPLAIN ANALYZE로 피드 쿼리 실행 계획 분석
2. WHERE IN 최적화 시도 (서브쿼리 vs 현재 방식)
3. Caffeine 캐시 튜닝 (maxSize, TTL 최적화)
4. (필요 시) Redis 피드 캐시 도입
