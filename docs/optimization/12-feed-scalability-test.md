## 분석

### 1. 팔로잉 수 vs 응답 시간 상관관계

```
팔로잉 수:    50    200    500   1000   2000   5000
avg (초):    6.56   6.18   5.96   6.32   8.34   7.49
```

- **50~1000**: 거의 차이 없음 (5.96~6.56s) → 현재 쿼리가 팔로잉 수와 무관하게 일정한 비용
- **2000+**: 급증 (8.34s, 7.49s) → 2000 이상에서 쿼리 비용이 눈에 띄게 증가
- **변곡점**: 팔로잉 1000 → 2000 사이에서 **32% 성능 저하**

### 2. 현재 피드 아키텍처의 문제

전체 그룹이 6초 이상 걸리는 것은 **피드 쿼리 구조 자체의 문제**:
- 팔로잉 50명이든 5000명이든 기본 6초 → 쿼리가 팔로잉 테이블 전체를 비효율적으로 스캔하거나
- N+1 쿼리 패턴 (댓글, 좋아요, 멤버 조회 등)이 팔로잉 수보다 더 큰 병목

### 3. 개선 방향

1. **피드 쿼리 구조 개선**: Push vs Pull 피드 모델 검토
2. **N+1 해소**: 피드 조회 시 필요한 연관 데이터 한 번에 가져오기 (Fetch Join / BatchSize)
3. **커서 기반 페이지네이션 최적화**: WHERE id < ? 기반 조회로 OFFSET 제거
4. **캐시 도입**: 인기 피드/핫 피드 Redis 캐시

> 팔로잉 수 증가에 따른 성능 저하보다, **기반 쿼리 최적화가 더 시급한 문제.**
> 2000명 이상에서 추가 32% 성능 저하가 발생하므로, 대량 팔로잉 유저에 대한 별도 전략도 필요.
