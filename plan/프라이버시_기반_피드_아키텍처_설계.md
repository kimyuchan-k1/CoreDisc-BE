## 1. 문제 발견

### 1-1. 시작 — 성능 최적화를 하다가 프라이버시 구멍을 발견

CoreDisc의 6단계 성능 최적화를 진행하면서, 피드 쿼리의 가시성 필터링 로직과 캐시 무효화 패턴을 깊이 분석하게 되었다. 그 과정에서 발견한 것:

**"관계가 변했는데, 콘텐츠 접근은 안 변하는 시간 창이 존재한다."**

CoreDisc는 일반적인 SNS와 달리 **3단계 가시성 모델**(OFFICIAL / CIRCLE / PERSONAL)을 가지고 있다. 이 3단계 모델은 사용자에게 세밀한 프라이버시 제어를 제공하지만, 동시에 **관계가 동적으로 변할 때 가시성의 일관성을 유지하기 어려운** 구조적 과제를 만든다.

일반 SNS의 public/private 2단계 모델에서는 관계 변경이 단순하다:
- 언팔로우 → 상대 글 안 보임. 끝.

하지만 CoreDisc에서는:
- Circle 해제 → CIRCLE 글만 안 보여야 하고, OFFICIAL 글은 여전히 보여야 함
- Block → 모든 글이 안 보여야 하고, 기존 좋아요/댓글도 정리되어야 함
- 관계 변경이 캐시, 피드, 상호작용 세 계층에 동시에 영향을 미침

**이 문제는 CoreDisc에 3단계 가시성 + 동적 Circle 관계가 있기 때문에 존재하는, 도메인 고유의 문제다.**

### 1-2. 왜 이 문제가 중요한가

```
CoreDisc는 "소셜 다이어리"다.
다이어리 = 개인의 내밀한 기록.
CIRCLE 글 = "가까운 사람에게만 보여주고 싶은 기록."

사용자가 누군가를 Circle에서 제거했다는 것은:
"이 사람에게 더 이상 내 내밀한 기록을 보여주고 싶지 않다."

그런데 제거한 후에도 5분간(캐시 TTL) 내 CIRCLE 글이 보인다면?
→ 사용자의 의도와 시스템의 행동이 불일치
→ 프라이버시에 대한 신뢰 상실
→ CIRCLE 기능 자체의 가치 훼손
```

**비즈니스 임팩트**:
- CIRCLE은 CoreDisc의 핵심 차별 기능. 이 기능이 신뢰되지 않으면 사용자는 모든 글을 PERSONAL로만 쓰거나, OFFICIAL로만 쓰게 됨 → 3단계 모델이 무의미해짐
- 소셜 다이어리에서 프라이버시 신뢰 = 서비스 존재 이유

## 2. 현재 상태 분석

### 2-1. 가시성 필터링의 현재 구조

현재 피드는 Pure Pull 모델이다. 사용자가 피드를 요청할 때마다 실시간으로 쿼리한다.

```
피드 조회 흐름:

① followingIds 조회 (Caffeine 캐시, 5분 TTL)
   → "내가 팔로우하는 사람들의 ID 목록"

② circleIds 조회 (Caffeine 캐시, 5분 TTL)
   → "내가 Circle로 마킹한 사람들의 ID 목록"

③ Post 쿼리 (QueryDSL)
   → WHERE 절에서 가시성 필터링:

   [ALL 피드]
   멤버 조건: 내 글 OR 팔로잉의 글
   가시성 조건:
     - OFFICIAL 글: 무조건 보임
     - CIRCLE 글: 작성자가 circleIds에 포함된 경우만
     - PERSONAL 글: 내가 작성자인 경우만

   [CORE 피드]
   멤버 조건: circleIds에 있는 사람의 글만
   가시성 조건:
     - OFFICIAL 글: 무조건 보임
     - CIRCLE 글: 작성자가 circleIds에 포함된 경우만
     - PERSONAL 글: 보이지 않음
```

### 2-2. 캐시 무효화의 현재 구조

관계 변경 시 캐시를 무효화하는 현재 패턴:

```
[팔로우 생성]
  → @CacheEvict("followingIds", key = 팔로워)
  → 팔로워의 followingIds 캐시만 무효화
  → 피팔로워의 캐시는 변경 없음 (영향 없으므로)

[언팔로우]
  → @CacheEvict("followingIds", key = 팔로워)
  → @CacheEvict("circleIds", key = 팔로워)
  → @CacheEvict("circleIds", key = 피팔로워)
  → 양쪽의 Circle 캐시 무효화 (Circle 관계도 해제되므로)

[Circle 상태 변경]
  → @CacheEvict("circleIds", key = 나)
  → @CacheEvict("circleIds", key = 상대)
  → 양쪽의 Circle 캐시 무효화

[Block]
  → @CacheEvict("followingIds", key = 나)
  → @CacheEvict("circleIds", key = 나)
  → @CacheEvict("followingIds", key = 상대)
  → @CacheEvict("circleIds", key = 상대)
  → 양쪽의 모든 캐시 무효화 + Follow 레코드 삭제

[Unblock]
  → (캐시 무효화 없음) ← 잠재적 버그
```

### 2-3. 현재 구조가 잘 작동하는 부분

공정하게 평가하면, 현재 구조는 **단일 서버 환경에서 대부분의 케이스를 잘 처리한다**:

```
잘 작동하는 것:
  ✓ Caffeine은 로컬 캐시이므로, @CacheEvict가 즉시 반영됨
  ✓ 캐시 MISS 시 DB에서 최신 데이터를 읽으므로 결국 정확해짐
  ✓ 5분 TTL이 있으므로 최악의 경우에도 5분 후에는 정확해짐
  ✓ 피드 쿼리의 가시성 필터링이 DB 레벨에서 정확히 작동함

잘 작동하지 않는 것 (이 설계서의 주제):
  ✗ @CacheEvict 누락된 케이스가 존재
  ✗ 캐시만 무효화하고, 기존 상호작용(좋아요/댓글)은 정리하지 않음
  ✗ 상호작용 시 가시성 검증이 없음
  ✗ 관계 변경의 부수효과가 여러 서비스에 흩어져 있음
```

## 3. Edge Case 카탈로그

코드 분석에서 발견한 프라이버시 관련 Edge Case 7가지:

### Case 1: Circle 해제 후 CIRCLE 글 지연 노출

```
시나리오:
  ① A가 B를 Circle에서 제거
  ② @CacheEvict("circleIds") 실행 → A의 circleIds 캐시 삭제
  ③ A가 바로 피드를 새로고침
  ④ circleIds 캐시 MISS → DB 조회 → B 제외된 새 목록 캐싱
  ⑤ B의 CIRCLE 글이 피드에서 사라짐 ✓

이건 정상 작동한다. 그런데 문제는 다른 곳에 있다:

실제 문제:
  ① A가 B를 Circle에서 제거
  ② A의 캐시는 즉시 무효화됨 ✓
  ③ 하지만 B의 입장에서: B가 A를 Circle로 마킹한 상태라면?
  ④ B의 circleIds에 A가 포함되어 있음
  ⑤ B의 피드에서 A의 CIRCLE 글이 보임
  ⑥ A가 B를 Circle에서 제거해도, B→A 방향의 Circle은 유지됨

  → 이것은 버그인가, 정상 동작인가?
```

**분석**: 현재 Circle의 의미는 **"내가 이 사람의 CIRCLE 글을 보겠다"**라는 단방향 선택이다. A가 B를 Circle에서 제거하면 A는 B의 CIRCLE 글을 안 보게 되지만, B가 A의 CIRCLE 글을 보는 것은 별개의 관계다.

하지만 사용자의 기대는 다를 수 있다. "나는 B를 Circle에서 뺐는데, B가 여전히 내 CIRCLE 글을 본다고?" → 이 기대 불일치가 프라이버시 문제.

**해결 방향**: Circle 해제를 양방향으로 처리할지, 아니면 "내 CIRCLE 글을 볼 수 있는 사람 목록"과 "내가 CIRCLE 글을 보는 사람 목록"을 분리할지 결정 필요.

### Case 2: Block 시 기존 좋아요/댓글 잔존

```
시나리오:
  ① B가 A의 글에 좋아요 10개, 댓글 5개를 남긴 상태
  ② A가 B를 Block
  ③ Block 처리:
     → A↔B 양방향 Follow 삭제 ✓
     → A, B 양쪽 캐시 전체 무효화 ✓
     → Block 엔티티 생성 ✓
  ④ 하지만:
     → B의 좋아요 10개가 A의 글에 남아있음 ✗
     → B의 댓글 5개가 A의 글에 남아있음 ✗
     → A의 글의 likeCount, commentCount에 B의 기여분 포함 ✗

결과:
  A가 자기 글에서 B의 댓글을 계속 보게 됨
  Block의 의미가 완전히 이행되지 않음
```

**현재 코드 확인**: `BlockCommandServiceImpl.block()`에서는 Follow 삭제와 캐시 무효화만 수행한다. PostLike, Comment에 대한 정리 로직은 없다.

**해결 방향**: Block 이벤트 발행 → 비동기로 기존 상호작용 정리

### Case 3: 좋아요/댓글의 가시성 검증 부재

```
시나리오:
  ① A가 CIRCLE 글을 작성 (Circle 멤버에게만 보이는 글)
  ② B는 A의 Circle이 아님
  ③ B가 어떤 경로로 A의 CIRCLE 글 postId를 알게 됨
     (예: API 직접 호출, 공유된 URL 등)
  ④ B가 POST /api/posts/{postId}/likes 요청
  ⑤ PostLikeCommandServiceImpl.createLike()에서:
     → Post 존재 확인 ✓
     → 중복 좋아요 확인 ✓
     → Post의 publicity 확인 ✗ ← 없음!
     → B의 좋아요가 성공적으로 생성됨
  ⑥ A에게 "B님이 좋아요를 눌렀습니다" 알림 발송

결과:
  Circle이 아닌 사람이 CIRCLE 글에 좋아요를 남길 수 있음
  댓글도 동일한 문제 (CommentCommandServiceImpl에도 가시성 체크 없음)
```

**현재 코드 확인**: `PostLikeCommandServiceImpl`과 `CommentCommandServiceImpl` 모두 Post의 publicity를 확인하지 않는다. Post 존재 여부와 중복 여부만 체크한다.

**해결 방향**: 상호작용 전에 가시성 검증 레이어 추가

### Case 4: Unblock 시 캐시 미갱신

```
시나리오:
  ① A가 B를 Block → 캐시 전체 무효화 ✓
  ② 시간이 지남 → 캐시에 "B 없는" followingIds가 올라감
  ③ A가 B를 Unblock
  ④ BlockCommandServiceImpl.unblock()에서:
     → Block 엔티티 삭제 ✓
     → 캐시 무효화 ✗ ← @CacheEvict 없음!
  ⑤ 하지만 Unblock 자체는 Follow를 복원하지 않으므로
     캐시가 갱신되지 않아도 실제 영향은 없음

분석:
  현재는 Unblock이 Follow를 복원하지 않으므로 캐시 미갱신이
  직접적인 프라이버시 문제를 일으키지는 않는다.

  하지만 코드의 일관성 관점에서 @CacheEvict가 없는 것은 잠재적 위험.
  향후 Unblock 로직이 변경될 때 캐시 관련 버그를 유발할 수 있다.
```

**심각도**: 낮음 (현재 로직에서는 실제 문제 없음)
**해결 방향**: 방어적으로 @CacheEvict 추가

### Case 5: Circle 해제 후 댓글/좋아요 알림 경로

```
시나리오:
  ① A가 B를 Circle로 설정
  ② B가 A의 CIRCLE 글에 댓글을 남김 (가시성이 있으므로 정당)
  ③ 시간이 지남
  ④ A가 B를 Circle에서 제거
  ⑤ B의 기존 댓글은 A의 글에 남아있음
  ⑥ C가 B의 댓글에 대댓글을 달면?
     → B에게 대댓글 알림이 감
     → B가 알림을 탭 → A의 CIRCLE 글로 이동
     → 하지만 B는 이제 A의 Circle이 아님
     → B가 A의 CIRCLE 글에 접근할 수 있는가?

분석:
  알림의 targetId로 Post에 직접 접근하는 경우,
  피드 가시성 필터링을 우회하게 됨.
  Post 상세 조회 API에서 가시성 체크를 하는지가 관건.
```

**해결 방향**: Post 상세 조회 API에도 가시성 검증 필요

### Case 6: Follow 알림의 동기 처리

```
현재 코드 분석:
  좋아요/댓글 알림: @Async + @TransactionalEventListener(AFTER_COMMIT)
  팔로우 알림: 동기 직접 호출 (이벤트 시스템 미사용)

문제:
  ① FollowCommandServiceImpl.follow() 내에서 직접:
     → NotificationCommandService.createNotification() 호출
     → deviceRepository.findByMemberAndIsActiveTrue() 호출
     → fcmService.sendNotificationToToken() 호출
  ② 이 모든 것이 @Transactional 안에서 실행됨
  ③ FCM 호출이 느리면(네트워크 지연) → Follow API 전체가 느려짐
  ④ FCM 호출이 실패하면 → Follow 트랜잭션이 롤백될 수 있음

분석:
  프라이버시 직접 문제는 아니지만, 관계 변경 이벤트 시스템의 일관성 문제.
  좋아요/댓글은 이벤트 기반인데 팔로우만 동기인 것은 아키텍처 불일치.
```

**해결 방향**: Follow 알림도 이벤트 기반으로 통일

### Case 7: 게시글 상세 조회의 가시성 검증

```
시나리오:
  ① B가 A의 CIRCLE 글 상세 페이지 URL을 브라우저에 북마크
  ② A가 B를 Circle에서 제거
  ③ B가 북마크를 통해 A의 CIRCLE 글 상세 페이지 접근
  ④ GET /api/posts/{postId}에서 가시성 체크를 하는가?

현재 코드 확인 필요:
  PostQueryServiceImpl.findPostDetail()에서
  Post의 publicity와 요청자의 관계를 검증하는지.

  만약 검증하지 않는다면:
  → postId만 알면 누구나 CIRCLE/PERSONAL 글에 접근 가능
  → 심각한 프라이버시 침해
```

**해결 방향**: 모든 Post 접근 경로에 가시성 검증 적용

### Edge Case 심각도 정리

| Case | 문제 | 심각도 | 실제 발생 가능성 |
|------|------|--------|---------------|
| 1 | Circle 해제의 양방향성 | 중 | 높음 |
| 2 | Block 후 좋아요/댓글 잔존 | **높음** | 높음 |
| 3 | 상호작용 가시성 미검증 | **높음** | 중 (API 직접 호출 필요) |
| 4 | Unblock 캐시 미갱신 | 낮음 | 중 |
| 5 | Circle 해제 후 알림 경로 접근 | 중 | 중 |
| 6 | Follow 알림 동기 처리 | 낮음 | - (프라이버시 문제 아님) |
| 7 | 상세 조회 가시성 미검증 | **높음** | 높음 |

## 4. 설계 원칙

### 원칙 1: 프라이버시는 즉시, 정리는 비동기

```
관계 변경이 발생했을 때:

즉시 처리해야 하는 것 (동기, 같은 트랜잭션):
  → 캐시 무효화 (다음 피드 요청에서 즉시 반영)
  → 가시성 플래그 변경

비동기로 처리해도 되는 것 (이벤트, 별도 트랜잭션):
  → 기존 좋아요/댓글 정리
  → 알림 발송
  → 카운터 보정

이유:
  "B가 내 CIRCLE 글을 더 이상 볼 수 없는 것"은 즉시 보장되어야 한다.
  "B의 기존 댓글이 내 글에서 사라지는 것"은 수 초~수 분 후에도 괜찮다.

  프라이버시 위반의 위험도와 처리 비용의 균형.
```

### 원칙 2: 읽기 경로에서 가시성 이중 검증

```
현재: 캐시된 circleIds로만 가시성 판단
  → 캐시가 오래되면 가시성이 부정확

개선: 캐시 + Read-time 검증 이중 방어
  ① 1차: 캐시된 circleIds로 피드 쿼리 (성능)
  ② 2차: Post 접근 시 실제 관계 확인 (정확성)

왜 이중 검증인가:
  → 피드 목록은 캐시 기반으로 빠르게 (약간의 부정확 허용)
  → 개별 Post 접근(상세, 좋아요, 댓글)은 정확하게 (프라이버시 보장)
  → 피드에서 잠깐 보이더라도, 클릭하면 접근 거부 → 프라이버시 최소한 보장
```

### 원칙 3: 관계 변경은 이벤트로 전파

```
현재: 관계 변경의 부수효과가 각 서비스에 흩어져 있음
  → FollowCommandServiceImpl: 캐시 무효화 + 알림 직접 발송
  → BlockCommandServiceImpl: 캐시 무효화 + Follow 삭제

문제:
  → 새로운 부수효과(좋아요 정리 등)를 추가하려면 기존 서비스를 수정해야 함
  → 관계 변경의 영향 범위를 한눈에 파악하기 어려움
  → 동기 처리와 비동기 처리가 혼재

개선: 관계 변경 → 도메인 이벤트 발행 → 리스너에서 부수효과 처리
  → 단일 책임: 관계 서비스는 관계만 변경
  → 확장성: 새 부수효과는 리스너 추가로 해결
  → 일관성: 모든 부수효과가 이벤트 기반으로 통일
```

### 원칙 4: 장애 격리

```
관계 변경의 핵심(Follow 생성/삭제, Circle 변경)이 성공하면,
부수효과(알림, 상호작용 정리)가 실패해도 핵심 동작은 보장되어야 한다.

현재 문제: Follow 알림이 동기 → FCM 장애 시 Follow 자체가 실패할 수 있음

개선: 핵심 동작과 부수효과의 트랜잭션 경계를 분리
  → @TransactionalEventListener(AFTER_COMMIT)
  → 핵심 트랜잭션 커밋 후에만 부수효과 실행
  → 부수효과 실패 시 핵심 동작에 영향 없음
```

## 5. 해결 1: 관계 변경 이벤트 시스템

### 5-1. 이벤트 설계

현재 CoreDisc에는 `NotificationEvent` 하나만 존재한다 (좋아요/댓글 알림용). 관계 변경에 대한 이벤트는 없다.

새로 도입할 관계 변경 이벤트:

```
[RelationshipEvent 계층]

RelationshipEvent (추상)
  ├── CircleChangedEvent
  │     → memberId: 누가
  │     → targetId: 누구를
  │     → isCircle: true(추가) / false(제거)
  │
  ├── BlockedEvent
  │     → blockerId: 누가
  │     → blockedId: 누구를
  │     → deletedFollowIds: 삭제된 Follow ID 목록
  │
  ├── UnfollowedEvent
  │     → memberId: 누가
  │     → targetId: 누구를
  │     → wasCircle: Circle이었는지
  │
  └── FollowedEvent
        → memberId: 누가
        → targetId: 누구를
```

### 5-2. 왜 기존 NotificationEvent를 확장하지 않는가

```
NotificationEvent: "누군가에게 알림을 보내라"
RelationshipEvent: "관계가 변경되었으니 필요한 조치를 취하라"

이 두 이벤트의 성격이 다르다:

NotificationEvent:
  - 단일 수신자 (알림 받는 사람)
  - 단일 동작 (Notification 저장 + FCM 발송)
  - 실패해도 서비스에 영향 없음

RelationshipEvent:
  - 다수의 관심 리스너 (캐시, 상호작용, 알림, 피드)
  - 다양한 동작 (캐시 무효화, 좋아요 정리, 알림 등)
  - 일부는 프라이버시에 직결 (캐시 무효화)

같은 이벤트 클래스로 처리하면:
  → 리스너가 비대해지고, 관심사가 혼합됨
  → 프라이버시 관련 처리와 알림 처리의 우선순위를 구분할 수 없음

분리하면:
  → 관계 변경의 영향을 받는 각 영역이 자기 리스너를 가짐
  → 리스너 추가/수정이 다른 리스너에 영향 없음
```

### 5-3. 이벤트 리스너 구조

```
[CircleChangedEvent 리스너들]

리스너 1: CacheInvalidationListener (동기, 높은 우선순위)
  → circleIds 캐시 즉시 무효화
  → 프라이버시 보장의 첫 번째 방어선
  → 이것은 기존 @CacheEvict가 하던 역할을 이벤트로 옮기는 것

리스너 2: InteractionCleanupListener (비동기)
  → Circle 제거 시: 제거된 유저의 CIRCLE 글에 대한
    기존 상호작용(좋아요/댓글)을 정리할지 결정
  → CoreDisc 정책 결정 필요: Circle 해제 시 기존 댓글을 삭제할 것인가?
  → 현재 결정: 기존 댓글/좋아요는 유지 (Circle 해제 ≠ Block)
  → Circle 해제는 "앞으로 안 보여줄게"이지 "기존 관계를 부정"하는 게 아님

리스너 3: NotificationListener (비동기)
  → 필요 시 관계 변경 알림 (현재는 Circle 변경 알림 없음)
```

```
[BlockedEvent 리스너들]

리스너 1: CacheInvalidationListener (동기)
  → 양쪽의 followingIds, circleIds 모두 무효화

리스너 2: InteractionCleanupListener (비동기)
  → 차단된 유저의 좋아요 삭제
  → 차단된 유저의 댓글 soft delete (isDeleted = true)
  → 관련 Post의 likeCount, commentCount 보정
  → 차단된 유저에게 보낸 알림 삭제

리스너 3: NotificationCleanupListener (비동기)
  → 차단된 유저로부터 받은 알림 삭제 또는 숨김
```

### 5-4. Circle 해제의 양방향성 결정

Case 1에서 제기된 질문: "A가 B를 Circle에서 빼면, B→A 방향의 Circle도 해제해야 하는가?"

```
[선택지]

A. 단방향 유지 (현재)
   → A가 B를 Circle에서 제거 = A가 B의 CIRCLE 글을 안 보겠다
   → B→A 관계는 그대로 = B는 여전히 A의 CIRCLE 글을 봄
   → 사용자 혼란: "나는 뺐는데 왜 상대가 내 글을 보지?"

B. 양방향 해제
   → A가 B를 Circle에서 제거하면, B→A Circle도 자동 해제
   → 양쪽 모두 상대의 CIRCLE 글을 안 보게 됨
   → 사용자 기대에 부합하지만, B가 원치 않는 관계 해제일 수 있음

C. "내 CIRCLE 글을 볼 수 있는 사람" 별도 관리
   → Circle 관계와 CIRCLE 글 가시성을 분리
   → 복잡도 대폭 증가 → 현 단계에서 과도한 설계

[결정: B (양방향 해제)]

근거:
  ① CoreDisc에서 Circle은 "서로 깊은 관계"를 의미
  ② 한쪽이 관계를 정리하면 양쪽 모두 정리되는 것이 자연스러움
  ③ 소셜 다이어리의 맥락에서 "나는 뺐는데 상대가 내 내밀한 글을 본다"는
     프라이버시 위반으로 느껴짐
  ④ 구현 복잡도가 낮음 (이미 양쪽 캐시를 무효화하고 있음)
  ⑤ B 입장에서 불편할 수 있지만, 프라이버시 > 편의성
```

### 5-5. Block 시 상호작용 정리 정책

Case 2에 대한 상세 정책 설계:

```
[Block 시 정리 대상]

① 차단된 유저가 내 글에 남긴 좋아요
   → 삭제
   → 내 글의 likeCount 감소
   → 이유: Block = "이 사람의 흔적을 보고 싶지 않다"

② 차단된 유저가 내 글에 남긴 댓글
   → soft delete (isDeleted = true, 내용은 "삭제된 댓글입니다"로 표시)
   → 내 글의 commentCount 감소
   → 이유: hard delete하면 대댓글 구조가 깨짐
   → soft delete로 내용만 가리고 구조는 유지

③ 내가 차단된 유저의 글에 남긴 좋아요/댓글
   → 삭제하지 않음
   → 이유: 차단을 당한 사람의 글에서 내 상호작용을 지우는 것은
           "차단"의 의미를 넘어서는 행위
   → 차단한 사람(나)의 글에서만 정리

④ 양방향 알림
   → 차단된 유저로부터 받은 알림 삭제
   → 내가 차단된 유저에게 보낸 알림은 유지 (상대의 데이터)
```

```
[왜 이 정책인가]

Instagram/Twitter 참고:
  → Block 시 상대의 좋아요/팔로우 해제
  → 댓글은 유지하되 상호작용 불가
  → 양쪽의 글에서 상대를 완전히 제거하지는 않음

CoreDisc 맥락:
  → 다이어리 앱이므로 "내 글에서 상대의 흔적 제거"가 더 중요
  → Block = "이 사람과의 관계를 끊겠다"
  → 내 공간(내 글)에서의 정리가 핵심
  → 상대 공간(상대 글)에서의 정리는 범위 밖
```

### 5-6. 이벤트 흐름 전체 그림

```
[현재 — 관계 변경의 부수효과가 흩어져 있음]

FollowCommandService.follow()
  ├── Follow 저장
  ├── 캐시 무효화 (@CacheEvict)
  ├── Notification 저장 (동기 직접 호출)
  └── FCM 발송 (동기 직접 호출)

BlockCommandService.block()
  ├── Block 저장
  ├── Follow 양방향 삭제
  ├── 캐시 무효화 (@CacheEvict)
  └── (좋아요/댓글 정리 없음!)

[개선 — 이벤트 기반으로 분리]

FollowCommandService.follow()
  ├── Follow 저장
  ├── 캐시 무효화 (즉시, 프라이버시)
  └── FollowedEvent 발행
        → NotificationListener: 알림 + FCM (비동기)

FollowCommandService.updateCircleStatus()
  ├── Circle 상태 변경
  ├── 캐시 무효화 (즉시, 프라이버시)
  └── CircleChangedEvent 발행
        → (Circle 제거 시) 양방향 Circle 해제 (비동기)

BlockCommandService.block()
  ├── Block 저장
  ├── Follow 양방향 삭제
  ├── 캐시 무효화 (즉시, 프라이버시)
  └── BlockedEvent 발행
        → InteractionCleanupListener: 좋아요/댓글 정리 (비동기)
        → NotificationCleanupListener: 알림 정리 (비동기)
```

```
변화 포인트:

① 캐시 무효화는 기존처럼 @CacheEvict로 즉시 처리 (변경 없음)
② 알림 발송이 동기 → 비동기로 전환 (Follow)
③ Block 시 상호작용 정리가 새로 추가 (이벤트 리스너)
④ Circle 해제 시 양방향 처리가 새로 추가 (이벤트 리스너)
```

## 6. 해결 2: 상호작용 레벨 가시성 검증

### 6-1. 문제 재정의

Case 3, 5, 7에서 발견한 공통 문제: **개별 Post에 접근하는 경로에서 가시성 검증이 없다.**

```
현재 가시성 검증이 존재하는 곳:
  ✓ 피드 목록 조회 (QueryPostRepositoryImpl.findPostFeed)
    → circleIds IN 조건으로 CIRCLE 글 필터링

현재 가시성 검증이 없는 곳:
  ✗ Post 상세 조회 (GET /api/posts/{postId})
  ✗ 좋아요 생성 (POST /api/posts/{postId}/likes)
  ✗ 댓글 생성 (POST /api/posts/{postId}/comments)
  ✗ 댓글 목록 조회 (GET /api/posts/{postId}/comments)

→ 피드에서는 안 보이지만, postId를 알면 직접 접근 가능
→ "문은 잠겨있지만 창문이 열려있는" 상태
```

### 6-2. 가시성 검증 서비스 설계

```
[PostVisibilityChecker — 단일 검증 지점]

역할: "이 유저가 이 Post에 접근할 수 있는가?"를 판단

입력: Post, 요청자 Member
출력: boolean (접근 가능 여부)

판단 로직:
  ① Post 작성자 == 요청자 → 항상 접근 가능 (본인 글)
  ② Post.publicity == OFFICIAL → 항상 접근 가능 (공개 글)
  ③ Post.publicity == PERSONAL → 작성자만 접근 가능
  ④ Post.publicity == CIRCLE → 요청자가 작성자를 Circle로 마킹했는지 확인
  ⑤ 요청자가 작성자를 Block 했거나, 작성자가 요청자를 Block 했으면 → 접근 불가
```

### 6-3. 왜 별도 서비스로 분리하는가

```
[선택지]

A. 각 서비스(Like, Comment, PostDetail)에서 개별적으로 검증
   → 코드 중복
   → 검증 로직 변경 시 여러 곳 수정 필요
   → 하나라도 빠뜨리면 보안 구멍

B. PostVisibilityChecker라는 단일 검증 서비스
   → 검증 로직이 한 곳에 집중
   → 모든 접근 경로에서 같은 검증기 호출
   → 정책 변경 시 한 곳만 수정
   → 테스트도 한 곳에서 집중

[결정: B]

이유:
  프라이버시 검증은 "절대 빠뜨리면 안 되는" 로직이다.
  여러 곳에 분산되면 하나를 놓칠 확률이 높아진다.
  단일 지점으로 모으면 "이 서비스를 통과하면 안전하다"는 보장이 가능하다.
```

### 6-4. 적용 지점

```
[가시성 검증이 필요한 API 목록]

높은 우선순위 (데이터 변경):
  POST /api/posts/{postId}/likes          → 좋아요 생성 전 검증
  DELETE /api/posts/{postId}/likes        → 좋아요 삭제 전 검증
  POST /api/posts/{postId}/comments       → 댓글 생성 전 검증
  POST /api/comments/{commentId}/replies  → 대댓글 생성 전 검증

중간 우선순위 (데이터 조회):
  GET /api/posts/{postId}                 → 상세 조회 전 검증
  GET /api/posts/{postId}/comments        → 댓글 목록 조회 전 검증

낮은 우선순위 (이미 필터링됨):
  GET /api/posts (피드)                   → 이미 QueryDSL에서 필터링 중
```

### 6-5. 성능 고려

```
가시성 검증에 필요한 정보:
  ① Post의 publicity (Post 엔티티에서 바로 확인)
  ② Post의 작성자 ID (Post 엔티티에서 바로 확인)
  ③ 요청자가 작성자를 Circle로 마킹했는지 (circleIds 캐시 활용)
  ④ Block 관계 여부 (추가 쿼리 필요)

성능 영향:
  → ①②: 이미 로드된 Post에서 확인, 추가 비용 0
  → ③: Caffeine 캐시 HIT 시 추가 비용 0, MISS 시 DB 쿼리 1회
  → ④: Block 확인 쿼리 1회 추가

Block 확인 최적화:
  → Block 관계는 변경 빈도가 낮으므로 캐시 가능
  → 하지만 Block은 "반드시 정확해야 하는" 데이터
  → DB 직접 조회가 안전 (exists 쿼리, 인덱스 활용 시 < 1ms)

총 추가 비용:
  Post 상세 조회: +1~2ms (Block 확인 쿼리)
  좋아요/댓글: +1~2ms (Block 확인 쿼리)
  → 수용 가능한 수준
```

### 6-6. 접근 거부 시 응답 설계

```
[가시성 검증 실패 시]

선택지:
  A. 403 Forbidden + "접근 권한이 없습니다"
     → 글의 존재 자체를 확인시킴 (정보 노출)

  B. 404 Not Found + "존재하지 않는 게시글입니다"
     → 글의 존재를 감추어 프라이버시 강화

  C. 상황에 따라 분기
     → Block된 유저: 404 (존재 자체를 숨김)
     → CIRCLE 미소속: 403 (권한 부족 명시)

[결정: B (404 통일)]

근거:
  ① 다이어리 앱에서 "이 글이 있는데 당신은 볼 수 없어요"는
     사용자에게 불필요한 호기심/불쾌감 유발
  ② 보안 관점에서 리소스 존재 여부 노출은 좋지 않음
  ③ 클라이언트 입장에서 403과 404를 다르게 처리할 필요 없음
     (어차피 보여줄 수 없으니 "없는 글" 처리)
  ④ Block된 유저에게 글 존재를 알려주면 Block의 의미 약화
```

## 7. 해결 3: 가시성 기반 선택적 피드 최적화

### 7-1. 현재 피드의 성능 특성

```
현재 Pure Pull 모델의 특성:

장점:
  → 항상 최신 데이터 반영 (실시간 가시성)
  → 캐시 일관성 문제 최소화
  → 구현이 단순

단점:
  → 매 요청마다 동일한 쿼리 반복
  → 팔로잉 1,000명 → WHERE member_id IN (1,000개 ID) 쿼리
  → 동시 접속자 증가 시 DB 부하 선형 증가

현재 성능 (Phase 6 최적화 후):
  → 피드 p95: 246ms
  → 쿼리 수: 7개 (캐시 HIT 기준)
  → 처리량: ~94 req/s
```

### 7-2. 가시성 기반 피드 캐시의 과제

일반 SNS에서는 피드 결과를 캐싱하기 쉽다. 하지만 CoreDisc에서는:

```
[일반 SNS의 피드 캐시]
키: feed:{userId}
값: [postId1, postId2, ...]
→ 팔로잉 변경 시 캐시 무효화 → 단순

[CoreDisc의 피드 캐시가 어려운 이유]

같은 피드 요청이라도 사용자마다 보이는 글이 다르다:

유저 A의 피드: [post1(OFFICIAL), post2(CIRCLE), post3(OFFICIAL)]
유저 B의 피드: [post1(OFFICIAL), post3(OFFICIAL)]
                 → post2는 CIRCLE이라 B에게 안 보임

유저 C의 피드: [post1(OFFICIAL), post2(CIRCLE), post3(OFFICIAL)]
                 → C도 작성자를 Circle로 마킹했으므로 post2 보임

→ 같은 작성자의 글이라도 publicity에 따라 유저마다 다르게 보임
→ "유저별 피드 캐시"를 만들어야 함
→ 캐시 키가 유저 수만큼 존재 → 메모리 부담
→ 관계 변경 시 어떤 유저의 캐시를 무효화해야 하는지 추적 필요
```

### 7-3. 선택적 최적화 전략

모든 피드를 캐싱하는 대신, **비용 대비 효과가 높은 부분만 최적화**:

```
[최적화 전략: 핫 콘텐츠 캐싱]

관찰:
  → 대부분의 피드 트래픽은 "최근 게시물"에 집중
  → 첫 페이지(최근 10개)가 전체 피드 조회의 80% 이상
  → 이전 페이지(커서 스크롤)는 상대적으로 적음

전략:
  → 피드의 "첫 페이지 후보군"만 사전 준비
  → 가시성 필터링은 여전히 Read-time에 수행
  → 하지만 DB 쿼리 대신 캐시된 후보군에서 필터링

구체적으로:
  ① 글이 발행되면 → 작성자의 팔로워 목록에서 활성 유저만 추출
  ② OFFICIAL 글: 전체 팔로워의 "후보 목록"에 추가
  ③ CIRCLE 글: Circle 멤버의 "후보 목록"에만 추가
  ④ 피드 조회 시: 후보 목록에서 읽어서 가시성 재검증 후 반환
  ⑤ 후보 목록이 없으면: 기존 DB 쿼리로 폴백
```

### 7-4. 왜 완전한 Push 모델을 도입하지 않는가

```
[완전한 Push 모델의 문제]

문제 1: Circle 변경 시 Push 데이터 정합성
  → A가 B를 Circle에서 제거
  → B의 타임라인에 이미 Push된 A의 CIRCLE 글은?
  → 삭제해야 함 → "Push된 데이터의 소급 정리" 필요
  → 복잡도 대폭 증가

문제 2: 프라이버시 이중 검증 불가
  → Push 모델에서는 Push 시점에 가시성이 결정됨
  → Read 시점에는 이미 타임라인에 있으므로 재검증이 어려움
  → Push 후 관계 변경 시 "이미 본 글"에 대한 처리 불명확

문제 3: 현재 규모에서 불필요
  → 유저 만 명, 피드 p95 246ms → 이미 충분히 빠름
  → Push 모델의 복잡도 대비 성능 이득이 크지 않음
  → 오버 엔지니어링

[CoreDisc에 맞는 선택: Pull 유지 + 선택적 캐싱]

Pull 모델의 장점을 유지:
  → Read 시점에 항상 최신 관계와 가시성 반영
  → 프라이버시 보장이 구조적으로 쉬움

선택적 캐싱으로 성능 개선:
  → 첫 페이지 후보군만 캐싱
  → 캐시에서 읽되, 가시성은 Read-time에 재검증
  → 캐시 없으면 기존 DB 쿼리로 폴백

이 결정은 "현재 규모"에서의 최적 선택이다.
유저가 10만 이상으로 성장하면 Push 하이브리드를 재고할 수 있다.
```

### 7-5. OFFICIAL 글에 대한 팔로워 수 기반 분기 (향후 확장)

```
[현재 규모에서는 불필요하지만, 설계 시 고려한 확장 포인트]

만약 유저 중 "인기 유저" (팔로워 500명 이상)가 등장한다면:

  일반 유저 (팔로워 < 500명):
    → 글 발행 시 팔로워들의 후보 목록에 직접 Push (fan-out on write)
    → 피드 조회 시 후보 목록에서 바로 읽기

  인기 유저 (팔로워 >= 500명):
    → 글 발행 시 작성자의 outbox에만 저장 (fan-out on read)
    → 피드 조회 시 팔로잉 중 인기 유저의 outbox에서 Pull + 병합

  하이브리드 피드 조회:
    → 후보 목록(Push된 글) + outbox(Pull한 글) 병합
    → 가시성 재검증
    → 커서 기반 페이지네이션

현재 결정:
  → 이 분기 로직은 v1에서 구현하지 않음
  → Pull 모델 + 가시성 검증 강화가 v1의 핵심
  → 확장이 필요한 시점에 후보 목록/outbox 인프라를 추가
```

```
[Circle 해제 흐름]

사용자 A가 B를 Circle에서 제거 요청

─── 동기 처리 (같은 트랜잭션) ─────────────────────

  ② A의 circleIds 캐시 무효화
  ③ B의 circleIds 캐시 무효화
  ④ CircleChangedEvent(A, B, false) 발행

─── 트랜잭션 커밋 ─────────────────────────────────

─── 비동기 처리 (AFTER_COMMIT) ───────────────────
  ⑥ CircleChangedEvent 리스너 실행
  ⑦ B→A Circle도 해제 (양방향 정리)
     → B→A Follow의 isCircle을 false로 변경
     → B의 circleIds 캐시 재무효화

  ⑦ 완료 후 B가 피드를 새로고침하면:
    → B의 circleIds에 A 없음 → A의 CIRCLE 글 안 보임 ✓ (수 초 후)

  ⑦ 전에 B가 피드를 새로고침하면:
    → B의 circleIds 캐시는 이미 ③에서 무효화됨
    → DB에서 새로 조회 → 아직 B→A isCircle=true
    → A의 CIRCLE 글이 잠깐 보일 수 있음 (⑦ 전까지)
    → 하지만 이 시간 창은 수 밀리초~수 초 수준
```

```
[Block 흐름]

사용자 A가 B를 Block 요청

─── 동기 처리 (같은 트랜잭션) ─────────────────────
  ① Block 엔티티 생성
  ② A→B Follow 삭제 (존재 시)
  ③ B→A Follow 삭제 (존재 시)
  ④ A, B 양쪽의 followingIds, circleIds 캐시 전체 무효화
  ⑤ BlockedEvent(A, B) 발행
  ⑥ 200 OK 응답
─── 트랜잭션 커밋 ─────────────────────────────────

─── 비동기 처리 (AFTER_COMMIT) ───────────────────
  ⑦ InteractionCleanupListener:
     → B가 A의 글에 남긴 좋아요 삭제
     → B가 A의 글에 남긴 댓글 soft delete
     → A의 글들의 likeCount, commentCount 보정

  ⑧ NotificationCleanupListener:
     → B로부터 A에게 온 알림 삭제
──────────────────────────────────────────────────

타이밍:
  ⑥ 직후 A가 피드를 새로고침하면:
    → followingIds에 B 없음 → B의 글 안 보임 ✓ (즉시)

  ⑥ 직후 B가 A의 글에 좋아요 시도하면:
    → PostVisibilityChecker에서 Block 확인 → 404 반환 ✓ (즉시)

  ⑦ 완료 후:
    → A의 글에서 B의 좋아요/댓글이 정리됨 ✓ (수 초 후)
```

### 8-3. 계층별 프라이버시 방어

```
[3중 방어 구조]

방어선 1: 캐시 무효화 (즉시)
  → 관계 변경 시 캐시를 즉시 삭제
  → 다음 피드 조회에서 DB 기반 최신 데이터 사용
  → "피드에서 안 보이게 하는" 첫 번째 방어선

방어선 2: PostVisibilityChecker (Read-time)
  → Post 개별 접근 시 가시성 검증
  → 피드를 우회한 직접 접근 차단
  → "개별 글에 접근 못하게 하는" 두 번째 방어선

방어선 3: 비동기 상호작용 정리 (Eventually)
  → Block 시 기존 좋아요/댓글 정리
  → 알림 정리
  → "흔적을 지우는" 세 번째 방어선

각 방어선의 역할:
  방어선 1: "안 보이게" (visibility)
  방어선 2: "접근 못하게" (access control)
  방어선 3: "흔적 지우기" (cleanup)

→ 방어선 1만으로도 프라이버시 기본 보장
→ 방어선 2가 추가되면 직접 접근도 차단
→ 방어선 3가 추가되면 과거 흔적까지 정리
→ 하나가 실패해도 다른 방어선이 보완
```

```
  → 총: ~6ms (비동기이므로 API 응답에 영향 없음)
```

### 9-2. 개선되는 부분

```
[Follow 알림의 비동기 전환]

현재: Follow API 내에서 동기로 알림 + FCM
  → FCM 호출: 100~500ms (네트워크 지연)
  → Follow API 전체 응답 시간에 포함

개선: 이벤트 기반 비동기
  → Follow API: Follow 저장 + 캐시 무효화만 → ~5ms
  → 알림 + FCM: 비동기 처리 → API 응답에 영향 없음
  → Follow API 응답 시간: 기존 대비 100~500ms 단축
```

```
  → 추가 쿼리 없음

  → 전체 p95에 미미한 영향
```

## 10. 의사결정 기록

### 결정 1: Pull 모델을 유지하고 Push를 도입하지 않는 이유

```
현재 규모: 유저 만 명, 피드 p95 246ms

Push 모델 도입 시:
  → 새로운 인프라: Redis Sorted Set (타임라인 저장소)
  → 새로운 비동기 파이프라인: fan-out 워커
  → 가시성 정합성 문제: Push 후 Circle 변경 시 소급 정리
  → 운영 복잡도: 타임라인 캐시 모니터링, 크기 관리

얻는 이득:
  → 피드 조회 시 DB 쿼리 감소
  → 응답 시간 개선 (이미 246ms로 충분히 빠름)

결론:
  "246ms를 100ms로 줄이기 위해 인프라 복잡도를 3배로 늘리는 것"은
  현재 단계에서 합리적이지 않다.

  프라이버시 보장이라는 당면 과제를 먼저 해결하고,
  규모가 커져서 Pull 모델이 한계에 도달하면 그때 Push를 고려한다.

포트폴리오 관점:
  "Push를 도입하지 않은 이유"를 설명할 수 있는 것이
  "Push를 도입했다"보다 더 성숙한 판단을 보여줌.
  기술은 문제를 해결하기 위한 수단이지 목적이 아니다.
```

### 결정 2: Block 시 상대 글에서의 정리를 하지 않는 이유

```
A가 B를 Block 할 때:
  ✓ B가 A의 글에 남긴 좋아요/댓글 → 정리
  ✗ A가 B의 글에 남긴 좋아요/댓글 → 정리하지 않음

이유:
  ① Block의 의미: "나는 이 사람과 관계를 끊겠다"
     → 내 공간(내 글)에서 상대의 흔적을 지우는 것은 당연
     → 상대 공간(상대 글)에서 내 흔적을 지우는 것은 "탈퇴"에 가까움

  ② 상대 관점: B는 Block 당한 것을 모를 수도 있음
     → B의 글에서 A의 댓글이 사라지면 B가 혼란
     → "내 글에 댓글이 있었는데 왜 사라졌지?"

  ③ 기술적 이유: 상대 글에서의 정리는 범위가 넓음
     → A가 B의 글 100개에 댓글을 남겼을 수 있음
     → 모두 찾아서 정리하려면 쿼리 비용 높음
     → Block은 빈번한 동작이 아니지만, 비용은 크면 안 됨

  ④ 업계 관행: Instagram, Twitter 모두
     → Block 시 상대의 팔로우만 해제
     → 상대 글에서의 내 활동은 정리하지 않음
```

### 결정 3: 404를 반환하는 이유 (403이 아닌)

```
보안 원칙: "최소 정보 노출 (Principle of Least Privilege)"

403 Forbidden:
  → "이 리소스가 존재하지만 당신은 접근할 수 없습니다"
  → 리소스 존재 여부를 확인시킴

404 Not Found:
  → "이 리소스를 찾을 수 없습니다"
  → 존재 여부 자체를 감춤

CoreDisc 맥락:
  → Block한 유저가 내 글 ID를 알고 403을 받으면:
    "아, 이 글이 있구나. 다른 계정으로 보면 되겠네."
  → 404를 받으면:
    "글이 없나보다." (존재 자체를 모름)

  → CIRCLE 글에 비Circle이 접근해서 403을 받으면:
    "CIRCLE 글이 있구나." (존재 확인)
  → 404를 받으면:
    "글이 없나보다." (프라이버시 보호)
```

### 결정 4: 캐시 무효화를 @CacheEvict로 유지하는 이유

```
[선택지]

A. 이벤트 리스너에서 캐시 무효화
   → 관계 변경 → 이벤트 발행 → 리스너에서 캐시 무효화
   → 장점: 모든 부수효과가 이벤트 기반으로 통일
   → 단점: 이벤트 처리 전까지 캐시가 오래된 상태

B. @CacheEvict를 유지하고, 이벤트는 추가 작업용
   → 관계 변경 → @CacheEvict 즉시 캐시 무효화 → 이벤트 발행
   → 장점: 캐시 무효화가 트랜잭션과 동기적으로 처리됨
   → 단점: 캐시 무효화가 어노테이션과 이벤트 두 곳에 분산

[결정: B]

근거:
  캐시 무효화는 프라이버시의 "첫 번째 방어선"이다.
  이벤트가 실패하거나 지연되어도 캐시는 이미 무효화된 상태여야 한다.
  @CacheEvict는 메서드 실행 시 즉시 발동하므로 가장 빠른 무효화 보장.

  이벤트 리스너는 @TransactionalEventListener(AFTER_COMMIT)이므로
  트랜잭션 커밋 후에 실행된다. 커밋 전까지 캐시가 유효하면
  그 사이에 다른 요청이 오래된 캐시를 사용할 수 있다.

  "프라이버시 보장은 가장 빠른 경로로" 원칙 적용.
```

## 부록: 포트폴리오 스토리 요약

```
[한 줄 요약]
"3단계 가시성 모델(OFFICIAL/CIRCLE/PERSONAL)에서
 관계 변경 시 프라이버시가 깨지는 7가지 Edge Case를 발견하고,
 3중 방어 구조로 해결했다"

[스토리 흐름]

1. 문제 발견
   → 성능 최적화를 하면서 피드의 가시성 필터링 코드를 분석
   → "관계가 변해도 콘텐츠 접근이 즉시 변하지 않는" 시간 창 발견
   → Block 후에도 좋아요/댓글이 남아있는 것 발견
   → Post 직접 접근 시 가시성 검증이 없는 것 발견

2. 문제의 구조적 원인 분석
   → 일반 SNS의 2단계(public/private)와 다른 3단계 모델의 복잡도
   → 캐시 무효화만으로는 모든 접근 경로를 방어할 수 없음
   → 관계 변경의 부수효과가 여러 서비스에 분산되어 있어 누락 발생

3. 설계 원칙 수립
   → "프라이버시는 즉시, 정리는 비동기"
   → "읽기 경로에서 이중 검증"
   → "관계 변경은 이벤트로 전파"

4. 3중 방어 구조 설계
   → 방어선 1: 캐시 즉시 무효화 (기존 강화)
   → 방어선 2: PostVisibilityChecker (신규)
   → 방어선 3: 비동기 상호작용 정리 (신규)

5. 의사결정
   → Pull 모델 유지, Push 도입하지 않은 이유
   → 404 vs 403 선택의 근거
   → Circle 양방향 해제 결정의 배경
   → Block 시 정리 범위 결정의 근거

6. 결과
   → 프라이버시 Edge Case 7가지 모두 해결
   → 성능 영향: Post 접근 시 +1~4ms (수용 가능)
   → Follow API: 비동기 전환으로 100~500ms 개선

[면접 예상 질답]

Q: "3단계 가시성이 왜 2단계보다 어려운가요?"
A: "public/private는 관계 변경 시 '전부 보이거나 전부 안 보이는' 이진 선택입니다.
    하지만 CIRCLE이라는 중간 계층이 있으면, Circle 해제 시 CIRCLE 글만 안 보이고
    OFFICIAL 글은 여전히 보여야 합니다. 관계 변경의 영향 범위가 publicity별로
    다르게 적용되어야 하므로, 캐시 무효화 + 접근 검증 + 상호작용 정리 세 계층
    모두에서 publicity를 고려해야 합니다."

Q: "Push 모델을 왜 도입하지 않았나요?"
A: "현재 피드 p95가 246ms이고 유저 만 명 규모에서 Pull로 충분합니다.
    Push를 도입하면 가시성 정합성 문제가 훨씬 복잡해집니다.
    Push 후 Circle이 변경되면 이미 Push된 CIRCLE 글을 소급 정리해야 하는데,
    이 복잡도 대비 현재 규모에서의 성능 이득이 크지 않습니다.
    기술은 문제를 해결하기 위한 수단이지 도입 자체가 목적이 아니라고 생각합니다."

Q: "Block 시 상대 글에서의 정리는 왜 안 하나요?"
A: "Block의 의미는 '나는 이 사람과 관계를 끊겠다'입니다.
    내 공간에서 상대의 흔적을 지우는 것은 당연하지만,
```
