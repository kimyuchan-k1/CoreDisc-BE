# 데이터 시딩 전략 & 부하 테스트 설계

## 배경

기존 시드 데이터(v1)는 uniform distribution으로 모든 유저가 동일한 활동량을 가지며, circle/block 데이터가 없어 피드 공개범위 필터링을 테스트할 수 없었다. k6 테스트도 읽기 전용이라 쓰기 부하와 hot key 시나리오가 빠져 있었다.

v2에서는 Power-law 분포 기반의 현실적인 시딩 전략과 read/write 혼합 부하 테스트를 도입한다.

## 유저 아키타입 (Power-law 분포)

| Tier | 이름 | 수 | ID 범위 | 팔로워 | 게시글 | 공개범위 (O/C/P) |
|------|------|-----|---------|--------|--------|------------------|
| T1 | Influencer | 10 | 1-10 | 500-1000 | 200-400 | 80/15/5% |
| T2 | Active | 500 | 11-510 | 50-100 | 50-100 | 60/30/10% |
| T3 | Normal | 4,500 | 511-5010 | 5-20 | 10-30 | 55/25/20% |
| T4 | Low-activity | 4,000 | 5011-9010 | 0-5 | 0-5 | 50/20/30% |
| T5 | Cold-start | 990 | 9011-10000 | 0 | 0 | - |

## 예상 데이터 볼륨

| 엔티티 | 볼륨 | 비고 |
|--------|------|------|
| Members | 10,000 | 기존과 동일 |
| Posts | ~138,500 | T1*300 + T2*75 + T3*20 + T4*2 |
| Comments | ~350,000 | T1 게시글에 집중 (power-law) |
| Follows | ~220,000 | T1이 가장 많은 팔로워 흡수 |
| Likes | ~280,000 | T1 게시글 50-1000개, T3 1-10개 |
| Blocks | ~500 | T2-T3 간 충돌 위주 |
| Circle Follows | ~15,000 | 상호팔로우의 15-60% (tier별 차등) |
| TodayQuestions | ~3,000,000 | 활성 유저별 활동기간 * 일 |
| Notifications | ~800,000 | 활동량 비례 |

## 핵심 설계 결정

### 팔로우 그래프
- T1 유저에 가중치 50x, T2에 5x, T3에 1x로 팔로워 분배
- 상호팔로우 식별 후 tier별 확률로 circle 지정

### Circle 구현 (코드 분석 기반)
`FollowCommandServiceImpl`에서 A가 B를 circle 지정 시, `follower_id=B, following_id=A` 행에 `is_circle=true` 설정. 피드 쿼리에서 `circleIds`는 `follower_id=memberId`인 follow 중 `is_circle=true`인 `following_id`를 반환.

### Block
Block 생성 시 양방향 follow 삭제. 피드에서 차단 유저 게시글 제외 검증.

### Hot Post
T1 유저의 상위 10개 게시글 (500-1000 likes)을 manifest에 기록.

### Denormalized Count 정합성
`like_count`, `comment_count`를 실제 레코드 수와 일치시킴 (UPDATE 문으로 보정).

### Manifest JSON
`hot_post_ids`, tier별 `member_ids`, `circle_pairs`, `block_pairs` → k6에서 import.

## k6 테스트 시나리오

### load-test-v2.js (메인 통합 테스트)

**시나리오 구조:**
- `read_heavy` (80%): 0→20→80→150 VUs, 10분, think time log-normal (0.5-2.2s)
- `write_operations` (20%): 0→5→20→30 VUs, 10분, think time log-normal (1-4.5s)

**Read 시나리오 가중치:**
- Feed ALL 25% / Feed CORE 10% / PostDetail 15% / Profile 10%
- Notifications 15% / Questions 10% / Search 5% / Comments 5% / HotPost 5%

**Write 시나리오 가중치:**
- CreatePost 25% / CreateComment 25% / Like/Unlike 20%
- Follow/Unfollow 15% / NotificationRead 15%

**SLI Thresholds:**
- feed p95 < 500ms
- post_create p95 < 1000ms
- error_rate < 5%

### hot-key-test.js (Hot Key 스트레스)
100 VUs가 동일한 3개 게시글에 동시 접근. GET detail + POST like + GET comments. 2분간 지속.

### circle-visibility-test.js (공개범위 검증)
manifest의 알려진 circle/block 쌍으로 7가지 edge case 검증:
1. Circle 멤버가 CIRCLE 게시글 조회 가능
2. 비-Circle 멤버는 CIRCLE 게시글 조회 불가
3. 차단된 유저 게시글 제외
4. 상호 차단 제외
5. PERSONAL 게시글은 본인만 조회
6. CORE 피드에서 circle 게시글만 반환
7. 언팔로우 시 피드에서 제외

## 검증 방법

1. **데이터 분포 검증** (SQL)
   ```sql
   -- tier별 팔로워 수 평균
   SELECT
     CASE
       WHEN m.id <= 10 THEN 'T1'
       WHEN m.id <= 510 THEN 'T2'
       WHEN m.id <= 5010 THEN 'T3'
       ELSE 'T4-T5'
     END AS tier,
     AVG(follower_cnt) AS avg_followers
   FROM member m
   LEFT JOIN (
     SELECT following_id, COUNT(*) AS follower_cnt
     FROM follow GROUP BY following_id
   ) f ON m.id = f.following_id
   GROUP BY tier;
   ```

2. **Denormalized count 정합성**
   ```sql
   SELECT p.id, p.like_count, COUNT(pl.id) AS actual_likes
   FROM post p
   LEFT JOIN post_like pl ON p.id = pl.post_id
   GROUP BY p.id
   HAVING p.like_count != COUNT(pl.id)
   LIMIT 10;
   ```

3. **Smoke 테스트**: `make test-smoke`로 API 정상 동작 확인
4. **Circle 가시성**: `make test-circle`로 7개 edge case 통과 확인
5. **Grafana 대시보드**: JVM Micrometer + k6 Load Testing 대시보드에서 SLI 지표 확인
