## 1. 문제 정의

### 1-1. CoreDisc의 사용자 여정

CoreDisc에서 사용자의 하루는 이렇게 시작된다:

```
앱 열기 → 오늘의 질문 3개 선택 → 질문에 답변 작성 → 피드에서 다른 사람 글 탐색
  ①             ②                    ③                    ④
```

**②(질문 선택)는 서비스의 첫 번째 능동적 행동이다.** 이 단계에서 이탈하면 ③, ④는 일어나지 않는다.

CoreDisc의 DAU(일일 활성 사용자)는 사실상 "매일 질문을 선택하고 답변을 작성하는 사람 수"와 같다. 피드 탐색만 하는 사용자는 콘텐츠를 소비할 뿐, 콘텐츠를 생산하지 않으므로 서비스의 핵심 가치 순환을 만들지 못한다.

### 1-2. 질문 선택의 구조적 피로

현재 CoreDisc의 질문 시스템:

| 구분 | 설명 |
|------|------|
| 고정 질문 (FIXED) | 월간 질문 3개 (order 1~3), 한 달 동안 같은 질문에 반복 답변 |
| 랜덤 질문 (RANDOM) | 매일 새로운 질문 1개 (order 4) |
| 질문 풀 | 시스템 기본 질문(DEFAULT) + 유저 공유 질문(OFFICIAL) + 개인 질문(PERSONAL) |
| 탐색 방법 | 카테고리 브라우징, 키워드 검색, 인기 질문(주간 Top 5) |

**문제의 핵심**: 사용자가 질문을 고르는 방법이 모두 **"사용자가 능동적으로 찾아야 하는"** 구조다.

- 카테고리 브라우징: 20개 이상의 카테고리를 직접 탐색해야 함
- 키워드 검색: 무엇을 검색해야 할지 모르면 무용지물
- 인기 질문: 전체 유저 대상 Top 5 → 나와 무관한 질문일 수 있음
- 랜덤 질문: 완전한 랜덤 → 맥락 없는 질문이 나올 수 있음

이 구조에서 발생하는 사용자 행동 패턴:

```
[패턴 A: 반복 선택]
→ 처음 몇 번은 다양한 질문을 탐색
→ 시간이 지나면 "이전에 쓴 질문"만 반복 선택
→ 자기 발견의 깊이가 정체됨

[패턴 B: 선택 포기]
→ "뭘 골라야 하지?"에서 멈춤
→ 앱을 닫거나, 아무거나 빠르게 선택
→ 답변의 질이 떨어지고, 서비스 가치를 느끼지 못함

[패턴 C: 이탈]
→ 매일 같은 탐색 과정을 반복하는 것에 피로
→ 답변 빈도가 줄어들고, 결국 앱을 열지 않게 됨
```

### 1-3. 비즈니스 임팩트

질문 선택 피로가 해소되지 않으면:

```
질문 선택 피로 증가
  → 답변 빈도 감소
    → 콘텐츠 생산 감소
      → 피드 콘텐츠 부족
        → 피드 탐색 가치 감소
          → 전체 서비스 활성도 하락
```

반대로, 좋은 질문 추천이 있으면:

```
"오늘 이 질문 어때요?" (맞춤 추천)
  → 질문 선택 시간 단축 (탐색 비용 제거)
    → 답변 작성으로 빠르게 진입
      → 다양한 카테고리의 질문에 노출
        → 자기 발견의 깊이와 폭이 확장
          → 서비스 핵심 가치 체감 → 리텐션 증가
```

### 1-4. 풀어야 할 질문

> **"현재 존재하는 데이터만으로, 사용자에게 '오늘 이 질문을 골라볼까?'라고 제안할 수 있는가?"**

이 설계서는 이 질문에 대한 답을 찾는 과정이다.

## 2. 현재 상태 분석

### 2-1. 질문 탐색 경로와 한계

현재 사용자가 질문을 찾는 경로:

```
경로 1: 카테고리 브라우징
  GET /api/questions/basic?categoryIds=1,2,3&size=20
  → OfficialQuestion + PersonalQuestion UNION ALL 결과
  → 커서 기반 페이지네이션 (createdAt, questionType, id)
  → 한계: 20+ 카테고리를 직접 탐색해야 함, 개인화 없음

경로 2: 키워드 검색
  GET /api/questions/basic/search?keyword=감정&size=20
  → UNION ALL + LIKE '%keyword%'
  → 한계: 검색어를 떠올려야 함, 새로운 발견이 어려움

경로 3: 인기 질문
  GET /api/questions/popular
  → 주간 저장 수(MemberOfficialQuestion count) 기준 Top 5
  → 한계: 모든 유저에게 같은 5개 추천, 나와의 관련성 없음

경로 4: 저장한 질문
  GET /api/questions/official/saved/mine
  → 내가 저장해둔 질문 목록
  → 한계: 저장한 것 중에서만 고르는 순환
```

### 2-2. 현재 "인기 질문"의 한계

현재 유일한 추천 메커니즘인 인기 질문(Popular Questions):

```
findTop5PopularQuestionsThisWeek()
  → 이번 주(월~일) MemberOfficialQuestion에서
  → OfficialQuestion별 저장 횟수 COUNT
  → 상위 5개 반환

문제:
  ① 전체 유저 대상 → 나와 무관한 질문
  ② 저장 수 기준 → "좋은 질문"이 아니라 "많이 저장된 질문"
  ③ 5개로 고정 → 선택지가 너무 적음
  ④ OfficialQuestion만 → PersonalQuestion, DEFAULT 제외
  ⑤ 이미 내가 답한 질문도 포함 → 중복 노출
```

### 2-3. 질문 선택 흐름에서의 마찰 지점

```
사용자가 "오늘의 질문"을 선택하려면:

[고정 질문 (order 1~3)]
  POST /api/questions/fixed
  body: { selectedQuestionType, questionOrder, questionId }

  → 사용자가 미리 질문 ID를 알아야 함
  → 브라우징 or 검색 → 질문 발견 → ID 확보 → 선택 요청
  → 이 과정이 매달 3번 반복됨

[랜덤 질문 (order 4)]
  POST /api/questions/random
  body: { selectedQuestionType, questionId }

  → 역시 사용자가 질문을 찾아야 함
  → "랜덤"이라는 이름과 달리 시스템이 랜덤 제공하는 게 아님
  → 사용자가 직접 고르는 구조

마찰 요약:
  "시스템은 질문을 제안하지 않는다. 사용자가 찾아오길 기다린다."
```

## 3. 데이터 탐색

### 3-1. 추천에 활용 가능한 기존 데이터

CoreDisc에는 이미 풍부한 사용자 행동 데이터가 존재한다. 새로운 데이터를 수집하지 않고도 추천을 만들 수 있다.

#### 신호 1: 질문 선택 이력 (TodayQuestion)

```
테이블: today_question
기록: 유저별, 날짜별, 어떤 질문을 골랐는지
빈도: 매일 최대 4건 (고정 3 + 랜덤 1)

활용 가능한 정보:
  - 유저 A가 최근 30일간 고른 질문 목록
  - 유저 A가 고른 질문의 카테고리 분포
  - 유저 A가 한 번도 선택하지 않은 카테고리
  - 어떤 질문이 가장 많이 선택되었는가 (전체 유저 기준)
  - 유저 A와 비슷한 질문을 고른 유저들은 누구인가
```

#### 신호 2: 질문 저장 행동 (MemberOfficialQuestion)

```
테이블: member_official_question
기록: 유저가 "이 질문 좋다"고 명시적으로 저장한 행위
빈도: 사용자의 능동적 행동 (저장 버튼 클릭)

활용 가능한 정보:
  - 유저가 관심 있는 질문의 성격/카테고리
  - 질문별 총 저장 수 (popularity signal)
  - "저장했지만 아직 답하지 않은 질문" 발견 가능
  - 유저 간 저장 패턴 유사도 (collaborative filtering 가능)
```

#### 신호 3: 답변 행동 (PostAnswer)

```
테이블: post_answer
기록: 유저가 질문에 대해 작성한 답변
빈도: 매일 최대 4건

활용 가능한 정보:
  - 답변 유형 (TEXT vs IMAGE) → 유저의 표현 선호
  - 텍스트 답변의 길이 → 질문에 대한 몰입도
  - "어떤 질문에 긴 답변을 쓰는가" → 깊이 있는 질문 식별
  - "어떤 질문에 이미지로 답하는가" → 시각적 질문 선호
```

#### 신호 4: 카테고리 체계 (QuestionCategory)

```
테이블: question_category
기록: 질문-카테고리 매핑 (N:N, 질문당 1~3개 카테고리)

활용 가능한 정보:
  - 유저의 카테고리 편향 (어떤 카테고리 질문을 주로 고르는가)
  - 카테고리 다양성 점수 (얼마나 다양한 카테고리를 시도했는가)
  - 유저가 아직 시도하지 않은 카테고리
  - 카테고리 간 동시 선택 패턴 (함께 쓰이는 카테고리)
```

#### 신호 5: 소셜 관계 (Follow + Circle)

```
테이블: follow (isCircle 플래그)
기록: 팔로우 관계 + 친한 친구(Circle) 여부

활용 가능한 정보:
  - 내 Circle 친구들이 최근 고른 질문
  - 내 팔로잉 사이에서 인기 있는 질문
  - "가까운 사람이 이 질문에 답했다" → 호기심 유발
```

#### 신호 6: 통계 데이터 (기존 배치 산출물)

```
테이블: daily_random_question_stat, monthly_fixed_question_stat
기록: 유저별 질문 선택 이력 (이미 배치로 집계 중)

활용 가능한 정보:
  - 월별 고정 질문 변경 패턴
  - 랜덤 질문의 카테고리 경향
  - 질문 선택의 시계열 변화
```

### 3-2. 신호별 특성 비교

| 신호 | 명시성 | 빈도 | 신뢰도 | 추천 활용 |
|------|--------|------|--------|----------|
| 질문 선택 (TodayQuestion) | 명시적 | 매일 4건 | 높음 | 핵심 신호 |
| 질문 저장 (MemberOfficialQuestion) | 명시적 | 비정기 | 매우 높음 | 관심 질문 신호 |
| 답변 길이/유형 (PostAnswer) | 암묵적 | 매일 4건 | 중간 | 몰입도 신호 |
| 카테고리 분포 (QuestionCategory) | 파생 | - | 높음 | 다양성 신호 |
| 소셜 관계 (Follow/Circle) | 명시적 | 비정기 | 높음 | 소셜 추천 |
| 통계 데이터 (Stats) | 집계 | 일/월 | 높음 | 트렌드 신호 |

### 3-3. 데이터에서 발견한 핵심 인사이트

**인사이트 1: "선택"과 "저장"은 다른 의도를 나타낸다**

```
TodayQuestion (선택) = "오늘 이 질문에 답하겠다" (행동 의도)
MemberOfficialQuestion (저장) = "이 질문이 마음에 든다" (관심 표현)

→ 저장했지만 선택하지 않은 질문 = "관심은 있지만 아직 답하지 않은 질문"
→ 이것이 추천의 첫 번째 후보군이 된다
```

**인사이트 2: 카테고리 다양성은 서비스 가치와 직결된다**

```
CoreDisc의 핵심 가치 = "자기 발견"
자기 발견 = 다양한 관점에서 자신을 돌아보는 것
→ 같은 카테고리 질문만 반복 선택 = 자기 발견의 정체
→ 카테고리 다양성을 높이는 추천 = 서비스 가치 극대화
```

**인사이트 3: Circle 관계는 "신뢰할 수 있는 취향 유사도"의 프록시다**

```
일반 팔로잉: "이 사람의 글이 흥미롭다"
Circle: "이 사람과 깊은 관계다, 서로의 일상을 공유한다"

→ Circle 친구의 질문 선택 = 나와 비슷한 맥락에서의 선택
→ 불특정 다수의 인기 질문보다 더 관련성 높은 추천
→ CoreDisc만이 가진 고유한 소셜 신호
```

## 4. 추천 전략 설계

### 4-1. 전략 개요

4가지 추천 전략을 조합하여 최종 추천 목록을 생성한다. 각 전략은 서로 다른 추천 목표를 가진다.

```
[추천 목록 구성]

전략 1: 미답변 저장 질문 (Unfinished Interest)
  → "저장해뒀는데 아직 안 써본 질문이 있어요"
  → 목표: 이미 관심을 보인 질문으로 전환율 극대화

전략 2: 카테고리 확장 추천 (Diversity Expansion)
  → "이 카테고리는 아직 시도해보지 않았어요"
  → 목표: 자기 발견의 폭을 넓히는 추천

전략 3: Circle 기반 추천 (Social Discovery)
  → "가까운 친구가 최근 이 질문에 답했어요"
  → 목표: 소셜 관계를 활용한 질문 발견

전략 4: 몰입도 기반 추천 (Engagement-driven)
  → "다른 사람들이 깊이 있게 답변한 질문이에요"
  → 목표: 질 높은 답변을 이끌어내는 질문 추천
```

### 4-2. 전략 1: 미답변 저장 질문 (Unfinished Interest)

#### 근거

사용자가 명시적으로 "저장"한 질문은 관심이 있다는 가장 강력한 신호다. 그런데 저장만 하고 답하지 않은 질문이 있다면, 이것은 "의도는 있었지만 시점이 안 맞았던" 질문이다.

#### 로직

```
① MemberOfficialQuestion에서 유저가 저장한 질문 ID 목록 조회
② TodayQuestion에서 유저가 이미 선택한 질문 ID 목록 조회 (최근 N일)
③ ①에서 ②를 뺀 차집합 = "저장했지만 답하지 않은 질문"
④ 저장 시간이 최신인 순서로 정렬 (최근 관심 우선)
```

#### 왜 이 전략이 첫 번째인가

```
전환율 관점:
  "아무 질문 추천" → 선택 확률 낮음 (관심 불확실)
  "이미 저장한 질문 추천" → 선택 확률 높음 (관심 확인됨)

→ 추천 시스템의 첫 번째 원칙: 확실한 신호부터 소진한다
→ 미답변 저장 질문은 가장 확실한 신호이므로 최우선
```

#### 한계

- 저장한 질문이 없는 신규 유저에게는 작동하지 않음 (cold start)
- 저장한 질문을 모두 소진하면 더 이상 추천할 것이 없음

### 4-3. 전략 2: 카테고리 확장 추천 (Diversity Expansion)

#### 근거

CoreDisc의 서비스 가치는 "자기 발견"이다. 같은 카테고리의 질문만 반복해서 고르면, 이미 아는 자신만 확인하게 된다. **아직 시도하지 않은 카테고리의 질문**을 추천함으로써, 사용자가 자기 발견의 새로운 관점을 얻게 할 수 있다.

#### 로직

```
① 유저의 최근 60일 질문 선택 이력에서 카테고리별 선택 횟수 집계
     → TodayQuestion → Question → QuestionCategory → Category
     → 결과: { "일상": 15회, "감정": 12회, "관계": 3회, "꿈": 0회, ... }

② 전체 카테고리 목록에서 선택 횟수가 0인 카테고리 식별
     → "미탐색 카테고리": [꿈, 가치관, 도전, ...]

③ 선택 횟수가 하위 30%인 카테고리도 "약탐색 카테고리"로 포함
     → 한두 번만 시도한 카테고리

④ 미탐색/약탐색 카테고리에서 질문 추출
     → 해당 카테고리의 질문 중 전체 유저 선택 수 상위 질문 우선
     → "남들은 많이 골랐는데 나는 안 골라본 질문"
```

#### 왜 이 전략이 중요한가

```
자기 발견의 깊이 vs 폭:

  깊이: 같은 카테고리(예: "감정")를 반복 탐색 → 감정에 대해 깊이 이해
  폭: 다양한 카테고리를 시도 → 다양한 관점에서 자신을 발견

CoreDisc가 추구하는 것은 둘 다이지만,
사용자는 자연스럽게 익숙한 카테고리에 편향됨 (confirmation bias)

→ 시스템이 "폭"을 넓혀주는 역할을 해야 함
→ 이것은 CoreDisc의 서비스 철학과 직결되는 추천 전략
```

#### 다양성 점수 (Diversity Score)

```
유저의 카테고리 다양성을 수치화:

Diversity Score = (선택한 적 있는 카테고리 수) / (전체 카테고리 수)

예시:
  전체 카테고리 20개, 유저가 8개 카테고리 사용
  → Diversity Score = 8/20 = 0.4

이 점수를 추천 로직에 반영:
  - Score < 0.3: 미탐색 카테고리 추천 비중 높임
  - Score 0.3~0.6: 균형 잡힌 추천
  - Score > 0.6: 깊이 있는 탐색 추천 (약탐색 카테고리 중 심화 질문)
```

### 4-4. 전략 3: Circle 기반 추천 (Social Discovery)

#### 근거

CoreDisc의 Circle은 "이 사람의 깊은 일상을 공유하고 싶다"는 의미를 담고 있다. 일반적인 SNS의 팔로우보다 훨씬 강한 관계 신호다.

Circle 친구가 최근 고른 질문은 두 가지 효과가 있다:
1. **관련성**: 가까운 관계일수록 관심사가 겹칠 확률이 높다
2. **호기심**: "내 친구가 이 질문에 뭐라고 답했을까?" → 같은 질문을 골라서 비교해보고 싶은 동기

이 두 번째 효과가 특히 중요하다. 같은 질문에 대해 서로 다른 답변을 쓰고 피드에서 비교하는 것은 CoreDisc의 소셜 다이어리 경험의 핵심이다.

#### 로직

```
① 유저의 Circle 멤버 목록 조회 (Caffeine 캐시 활용 가능)
② Circle 멤버들의 최근 7일 질문 선택 이력 조회
     → TodayQuestion WHERE member_id IN (circleIds)
       AND selected_date >= (오늘 - 7일)
③ 내가 아직 선택하지 않은 질문만 필터링
④ 같은 질문을 고른 Circle 멤버 수로 정렬 (많을수록 우선)
```

#### 왜 Circle이고 Follow가 아닌가

```
Follow 관계: "이 사람의 글이 흥미롭다" (약한 관계)
Circle 관계: "이 사람과 깊은 관계다" (강한 관계)

Follow 기반 추천의 문제:
  - 팔로잉 100명 → 너무 많은 질문이 나옴 → 노이즈
  - 관계 강도를 모르므로 관련성 보장 불가

Circle 기반 추천의 장점:
  - 일반적으로 5~20명 수준 → 적절한 추천 후보 수
  - 강한 관계 = 높은 관련성
  - "친한 친구가 이 질문에 답했다" → 더 강한 동기 부여

→ CoreDisc에 Circle이라는 관계 계층이 존재하기 때문에 가능한 전략
→ 일반적인 SNS에서는 이 수준의 관계 기반 추천이 어려움
```

#### Cold Start 대응

```
Circle이 0명인 유저:
  → 전략 3 건너뛰기
  → 전략 1, 2, 4로 보완

Circle이 있지만 최근 7일 활동이 없는 경우:
  → 기간을 14일로 확장
  → 그래도 없으면 건너뛰기
```

### 4-5. 전략 4: 몰입도 기반 추천 (Engagement-driven)

#### 근거

어떤 질문은 사용자가 더 깊이 생각하게 만든다. 이를 "좋은 질문"이라고 정의할 수 있다.
현재 인기 질문(Popular)은 저장 수로만 판단하는데, "많이 저장된 질문"이 반드시 "좋은 답변을 이끄는 질문"은 아니다.

**"좋은 질문"의 프록시 지표**: 답변의 평균 텍스트 길이.
- 긴 텍스트 답변 = 사용자가 깊이 생각하고 많이 쓴 것
- 짧은 답변이나 이미지만 올린 경우 = 가볍게 넘긴 것

#### 로직

```
① 최근 30일간 전체 유저의 답변 데이터 분석 (배치)
② TodayQuestion → PostAnswer 매핑
     → 질문별로 답변 데이터 집계
③ 질문별 몰입도 점수(Engagement Score) 계산:

     Engagement Score = (평균 텍스트 답변 길이) × (답변 수 가중치)

     - 평균 답변 길이: 해당 질문을 선택한 유저들의 텍스트 답변 평균 글자 수
     - 답변 수 가중치: 최소 N명 이상 답한 질문만 유효 (통계적 신뢰)

④ 내가 아직 선택하지 않은 질문 중 Engagement Score 상위 추천
```

#### 왜 답변 길이인가

```
대안 1: 좋아요 수
  → 좋아요는 글(Post) 단위이지 질문 단위가 아님
  → 좋은 답변이 좋아요를 받는 거지, 좋은 질문이 받는 게 아님
  → 부적합

대안 2: 저장 수 (현재 인기 질문)
  → "많이 저장됨" = "질문 문장이 매력적"
  → 하지만 실제로 답하면 얕은 답변만 나올 수 있음
  → 약한 신호

대안 3: 답변 작성률
  → 질문 선택 후 실제 답변까지 완료한 비율
  → 하지만 현재 데이터로는 "선택했지만 답 안 한 케이스"를 정확히 추적하기 어려움
  → 추후 고려

답변 길이:
  → "이 질문에 대해 할 말이 많았다" = 깊이 있는 사고를 유발한 질문
  → PostAnswer.textContent의 LENGTH로 바로 계산 가능
  → 기존 데이터에서 추출 가능, 추가 수집 불필요
```

### 4-6. 4가지 전략의 조합

#### 추천 슬롯 배분

총 10개의 추천 질문을 반환한다고 가정:

```
[기본 배분 비율]

전략 1 (미답변 저장):     최대 3개 (최우선, 있는 만큼)
전략 2 (카테고리 확장):   3개
전략 3 (Circle):         2개
전략 4 (몰입도):         2개

→ 전략 1의 결과가 3개 미만이면, 나머지 슬롯을 전략 2로 보충
→ 전략 3의 결과가 0개이면 (Circle 없음), 전략 4로 보충
```

#### 왜 이 비율인가

```
전략 1 (최우선): 전환율이 가장 높은 전략 → 가능한 한 많이 채움
전략 2 (3개):   서비스 가치(자기 발견)에 직결 → 항상 포함되어야 함
전략 3 (2개):   소셜 동기 부여 → 있으면 효과적이지만 없어도 됨
전략 4 (2개):   보편적 품질 보장 → 다른 전략이 부족할 때 보완

이 비율은 초기 설정이며, 추후 데이터를 보고 조정한다.
```

#### 중복 제거 및 필터링

```
전체 추천 목록에서 제거해야 하는 질문:

① 이미 현재 TodayQuestion으로 설정된 질문 (오늘 이미 선택한 것)
② 최근 7일 이내에 답변한 질문 (너무 최근에 쓴 것)
③ 유저가 차단(Block)한 사람이 만든 질문
④ 삭제된 질문

→ 각 전략의 결과를 합친 후 일괄 필터링
→ 필터링 후 10개 미만이면 전략 4(몰입도)로 추가 보충
```

## 5. 추천 파이프라인 아키텍처

### 5-1. 실시간 계산 vs 사전 계산

추천 시스템에서 가장 중요한 아키텍처 결정: **언제 계산할 것인가?**

```
[선택지 1: 완전 실시간]
API 요청 → 4가지 전략 각각 DB 쿼리 → 조합 → 응답

장점: 항상 최신 데이터 반영
단점: 매 요청마다 복잡한 쿼리 5~10개 실행 → 응답 지연

[선택지 2: 완전 사전 계산]
배치 → 유저별 추천 목록 생성 → Redis 저장
API 요청 → Redis에서 읽기 → 응답

장점: API 응답 매우 빠름
단점: 배치 주기만큼 데이터가 오래됨, 저장 공간 필요

[선택지 3: 하이브리드]
무거운 계산(전략 2, 4)은 배치로 사전 계산
가벼운 계산(전략 1, 3)은 실시간 처리

장점: 응답 속도와 데이터 신선도 균형
단점: 두 가지 경로를 관리해야 함
```

#### 결정: 하이브리드 (선택지 3)

```
[전략별 계산 시점 결정 근거]

전략 1 (미답변 저장):
  → 저장/선택 행위가 수시로 발생 → 실시간이어야 최신 반영
  → 쿼리 복잡도: 낮음 (차집합 연산)
  → 결정: 실시간

전략 2 (카테고리 확장):
  → 60일 선택 이력 기반 → 하루 단위로 변해도 충분
  → 쿼리 복잡도: 중간 (다중 JOIN + GROUP BY)
  → 결정: 일 1회 배치 사전 계산

전략 3 (Circle):
  → Circle 멤버의 최근 선택 → 실시간에 가까울수록 좋음
  → 쿼리 복잡도: 낮음 (circleIds는 캐시 있음)
  → 결정: 실시간 (캐시 활용)

전략 4 (몰입도):
  → 30일 전체 유저 답변 분석 → 무거운 집계 쿼리
  → 질문의 몰입도 점수는 매일 크게 변하지 않음
  → 결정: 일 1회 배치 사전 계산
```

### 5-2. 전체 파이프라인

```
[배치 파이프라인 — 매일 새벽 실행]

┌──────────────────────────────────────────────────┐
│  Daily Recommendation Batch                       │
│                                                    │
│  ① 전략 2: 유저별 카테고리 분포 분석               │
│     → 전체 유저의 60일 선택 이력 집계               │
│     → 유저별 미탐색/약탐색 카테고리 추출            │
│     → 해당 카테고리의 추천 질문 선정                │
│     → Redis 저장: rec:diversity:{userId}           │

│  ② 전략 4: 질문별 몰입도 점수 계산                 │
│     → 30일 전체 답변 데이터 집계                    │
│     → 질문별 평균 답변 길이 계산                    │
│     → Engagement Score 상위 질문 선정               │
│     → Redis 저장: rec:engagement (전체 공유)        │
│                                                    │
└──────────────────────────────────────────────────┘

[실시간 파이프라인 — API 요청 시]

┌──────────────────────────────────────────────────┐
│  GET /api/questions/recommendations               │
│                                                    │
│  ① 전략 1: 미답변 저장 질문 (실시간 쿼리)          │
│     → 저장 질문 - 최근 선택 질문 = 미답변 목록      │
│                                                    │
│  ② 전략 2: Redis에서 사전 계산 결과 읽기            │
│     → rec:diversity:{userId}                       │
│                                                    │
│  ③ 전략 3: Circle 추천 (실시간 쿼리)               │
│     → circleIds (Caffeine 캐시) → 최근 선택 질문    │
│                                                    │
│  ④ 전략 4: Redis에서 사전 계산 결과 읽기            │
│     → rec:engagement                               │
│                                                    │
│  ⑤ 조합 + 필터링 + 중복 제거                       │
│     → 이미 선택한 질문 제외                         │
│     → Block 유저 질문 제외                          │
│     → 슬롯 배분 규칙에 따라 10개 선정               │
│                                                    │
│  ⑥ 응답 반환                                      │
└──────────────────────────────────────────────────┘
```

### 5-3. 왜 이 구조인가

```
[실시간 계산만 하면 안 되는 이유]

전략 2의 쿼리:
  → 유저 1명의 60일 선택 이력 → TodayQuestion JOIN QuestionCategory
  → 카테고리별 GROUP BY → 전체 카테고리와 비교
  → 미탐색 카테고리의 인기 질문 조회
  → 최소 3~4개 쿼리, 조인 2~3단계

이것이 피드 조회만큼 빈번하게 호출되면:
  → DB 부하 증가 → 피드 등 다른 핵심 API 응답에 영향
  → 추천 API 자체도 느려짐 (200ms+ 예상)

[사전 계산만 하면 안 되는 이유]

전략 1의 특성:
  → 유저가 질문을 저장한 직후, 추천 목록에 반영되어야 자연스러움
  → 배치 주기(1일)까지 기다리면 "방금 저장한 질문"이 추천에 안 나옴
  → 사용자 경험 손상

전략 3의 특성:
  → Circle 친구가 오늘 질문을 고른 것이 오늘 내 추천에 반영되어야 의미 있음
  → 어제의 Circle 활동은 "소셜 동기 부여" 효과가 약함

[하이브리드의 균형점]

  배치: 무거운 집계는 새벽에 한 번 (DB 부하 분산)
  실시간: 가벼운 조회는 요청 시 (신선한 데이터)
  Redis: 배치 결과 캐싱 (실시간 API의 응답 속도 보장)
```

## 6. API 설계

### 6-1. 추천 질문 조회 API

```
GET /api/questions/recommendations

목적: 유저 맞춤 추천 질문 목록 반환
인증: 필요 (@CurrentMember)
```

#### 요청 파라미터

```
size: 추천 질문 수 (기본값: 10, 최대: 20)
```

사이즈 외에 별도의 파라미터를 받지 않는다. 추천의 핵심은 **사용자가 아무것도 입력하지 않아도 적절한 결과가 나오는 것**이다.

#### 응답 구조

```
{
  "recommendations": [
    {
      "questionId": Long,
      "questionType": "DEFAULT" | "OFFICIAL" | "PERSONAL",
      "question": "질문 내용",
      "categories": [
        { "id": Long, "name": "카테고리명" }
      ],
      "recommendReason": "UNFINISHED_INTEREST" | "DIVERSITY" | "CIRCLE" | "ENGAGEMENT",
      "reasonDetail": "저장해뒀던 질문이에요" | "아직 시도해보지 않은 카테고리예요" | ...,
      "savedStatus": "SAVED" | "NOT_SAVED",
      "circleFriendCount": 2  // CIRCLE 전략일 때만, 이 질문을 고른 Circle 친구 수
    }
  ],
  "diversityScore": 0.4,  // 유저의 현재 카테고리 다양성 점수
  "totalCategoryCount": 20,
  "exploredCategoryCount": 8
}
```

#### recommendReason 필드의 의미

```
왜 추천 이유를 노출하는가:

① 투명성: "왜 이 질문을 추천했는지" 사용자가 알 수 있음
② 설득력: "친구가 답한 질문" vs 랜덤 질문 → 전자가 선택 동기 더 강함
③ 차별화: 단순 "추천 질문" 나열이 아닌, 맥락이 있는 추천
④ 디버깅: 추천 전략별 클릭률을 추적하여 전략 효과 측정 가능
```

### 6-2. 추천 피드백 API (추후 확장)

```
POST /api/questions/recommendations/{questionId}/feedback

목적: 추천 질문에 대한 사용자 반응 기록
용도: 추천 품질 측정 및 개선

요청:
{
  "action": "SELECTED" | "DISMISSED" | "SAVED"
  "recommendReason": "DIVERSITY"  // 어떤 전략의 추천이었는지
}
```

이 API는 v1에서 필수는 아니다. 하지만 **설계 단계에서 확장 가능성을 고려한 것**은 포트폴리오 관점에서 의미가 있다. "추천 품질을 어떻게 측정하고 개선할 것인가?"에 대한 답을 제시하기 때문이다.

### 6-3. 기존 API와의 관계

```
[기존 질문 탐색 API는 유지]

GET /api/questions/basic         → 카테고리 브라우징 (능동 탐색)
GET /api/questions/basic/search  → 키워드 검색 (능동 탐색)
GET /api/questions/popular       → 인기 질문 (수동 발견)

[새로 추가]

GET /api/questions/recommendations → 개인화 추천 (맞춤 발견)

→ 기존 API는 "내가 찾으러 가는" 경로
→ 추천 API는 "시스템이 찾아주는" 경로
→ 두 경로는 보완적이며, 추천이 기존 경로를 대체하지 않음
```

## 7. 저장소 설계

### 7-1. Redis 키 구조

```
[전략 2: 카테고리 확장 추천 — 유저별]

키: rec:diversity:{userId}
타입: String (JSON)
TTL: 25시간 (배치 주기 24시간 + 여유 1시간)
값: {
  "unexploredCategories": [5, 12, 17],       // 미탐색 카테고리 ID
  "weakCategories": [3, 8],                   // 약탐색 카테고리 ID
  "recommendedQuestionIds": [101, 205, 342],  // 추천 질문 ID
  "diversityScore": 0.4,                      // 다양성 점수
  "calculatedAt": "2026-03-02T03:00:00"
}

사이즈 추정:
  유저당 ~200 bytes
  10,000 유저 → ~2MB
  → Redis 메모리 부담 최소
```

```
[전략 4: 몰입도 기반 추천 — 전체 공유]

키: rec:engagement
타입: String (JSON)
TTL: 25시간
값: {
  "questions": [
    { "questionId": 101, "score": 85.3, "avgLength": 127 },
    { "questionId": 205, "score": 78.1, "avgLength": 112 },
    ...
  ],
  "calculatedAt": "2026-03-02T03:00:00"
}

사이즈 추정:
  상위 100개 질문 × ~50 bytes = ~5KB
  전체 유저 공유 → 키 1개
  → Redis 부담 없음
```

### 7-2. 왜 Redis인가

```
대안 1: DB 테이블에 저장
  → 배치 결과를 recommendation 테이블에 INSERT
  → 장점: 영속성 보장
  → 단점: 임시 데이터인데 DB 공간 차지, 매일 DELETE + INSERT 필요
  → 추천 결과는 "24시간 유효한 임시 데이터" → DB에 맞지 않음

대안 2: Caffeine 로컬 캐시
  → 서버 메모리에 저장
  → 장점: 가장 빠른 읽기
  → 단점: 서버 재시작 시 소멸, 다중 서버 시 일관성 문제
  → 배치 결과는 서버 간 공유되어야 함 → 로컬 캐시 부적합

대안 3: Redis
  → TTL 기반 자동 만료 → 임시 데이터에 적합
  → 서버 간 공유 → 다중 서버 환경 지원
  → 이미 프로젝트에 Redis 인프라 존재 → 추가 비용 없음
  → 적합
```

### 7-3. 추천 통계 테이블 (신규)

추천 효과를 측정하기 위해 추천 이벤트를 기록하는 테이블:

```
[recommendation_log]

목적: 추천 → 선택 전환율 추적
생명주기: 장기 보관 (분석용)

필드:
  - id (PK)
  - member_id (FK)
  - question_id (FK)
  - recommend_reason (ENUM: UNFINISHED_INTEREST, DIVERSITY, CIRCLE, ENGAGEMENT)
  - action (ENUM: IMPRESSED, SELECTED, DISMISSED)
  - created_at (TIMESTAMP)

인덱스:
  - idx_reclog_member_created (member_id, created_at) — 유저별 이력
  - idx_reclog_reason_action (recommend_reason, action) — 전략별 전환율 집계
```

이 테이블이 필요한 이유:

```
"추천 시스템을 만들었다"만으로는 포트폴리오가 약하다.
"전략별 전환율을 측정하고, 데이터에 기반해 비율을 조정했다"가 있어야 강하다.

recommendation_log를 통해:
  ① 어떤 전략의 추천이 가장 많이 선택되는지 (전환율)
  ② 어떤 전략의 추천이 가장 많이 무시되는지 (이탈율)
  ③ 시간에 따른 추천 효과 변화 추적

→ 데이터 기반 의사결정의 근거가 됨
```

## 8. 성능과 확장성 고려

### 8-1. 실시간 쿼리 성능

```
[전략 1: 미답변 저장 질문 — 실시간 쿼리 분석]

쿼리 1: 유저의 저장 질문 ID 목록
  SELECT official_question_id, personal_question_id
  FROM member_official_question
  WHERE member_id = ?
  → 인덱스: FK(member_id) → 빠름
  → 예상 결과 수: 유저당 10~50건

쿼리 2: 유저의 최근 선택 질문 ID 목록
  SELECT official_question_id, personal_question_id
  FROM today_question
  WHERE member_id = ? AND selected_date >= ?
  → 인덱스: idx_tq_member_order_date → 빠름
  → 예상 결과 수: 최근 7일 × 4개 = 28건

차집합 연산: 애플리케이션 레벨에서 Set 연산
  → O(N) where N = 저장 질문 수 → 무시 가능

총 예상 시간: 2~5ms
```

```
[전략 3: Circle 추천 — 실시간 쿼리 분석]

쿼리 0: Circle 멤버 ID 목록
  → Caffeine 캐시에서 조회 (HIT 시 0ms)
  → MISS 시: Follow 테이블 쿼리 (~2ms)

쿼리 1: Circle 멤버의 최근 질문 선택
  SELECT tq.official_question_id, tq.personal_question_id, tq.member_id
  FROM today_question tq
  WHERE tq.member_id IN (:circleIds)
    AND tq.selected_date >= :sevenDaysAgo
  → 인덱스: idx_tq_member_order_date → IN 쿼리
  → 예상 결과 수: Circle 10명 × 7일 × 4개 = 280건 (최대)

총 예상 시간: 3~8ms (캐시 HIT 기준)
```

```
[전체 추천 API 예상 응답 시간]

전략 1 (실시간):     2~5ms
전략 2 (Redis 읽기): 1~2ms
전략 3 (실시간):     3~8ms
전략 4 (Redis 읽기): 1~2ms
조합 + 필터링:       1~2ms

총 예상: 8~19ms → 50ms 이내 목표 충분히 달성 가능
```

### 8-2. 배치 성능

```
[전략 2 배치: 유저별 카테고리 분포 분석]

쿼리: 전체 유저의 60일 질문 선택 + 카테고리 JOIN
  → 유저 10,000명 × 60일 × 4건 = 최대 2,400,000 행
  → 한 번에 전체를 읽으면 메모리 부담

해결: 청크 단위 처리 (기존 배치 패턴과 동일)
  → 유저 100명 단위로 분할 처리
  → 유저 100명의 60일 선택 이력 = ~24,000행 → 관리 가능
  → 100명 처리 → Redis 저장 → 다음 100명

예상 총 실행 시간: 유저 10,000명 기준 5~10분
```

```
[전략 4 배치: 질문별 몰입도 점수 계산]

쿼리: 30일간 전체 답변의 질문별 평균 길이
  → GROUP BY question_id, AVG(LENGTH(text_content))
  → 하나의 집계 쿼리로 처리 가능
  → 인덱스: 필요 시 추가 (post_answer에 대한 집계)

예상 실행 시간: 1~3분 (단일 집계 쿼리)
```

### 8-3. 확장성 고려

```
[유저 수 증가 시]

10,000 유저:
  → 배치 5~10분, Redis 2MB → 문제 없음

100,000 유저:
  → 배치 50~100분 → 병렬 처리 필요
  → Redis 20MB → 여전히 문제 없음
  → 해결: 배치를 ThreadPoolTaskExecutor로 병렬화 (기존 패턴 활용)

1,000,000 유저:
  → 배치 병렬화 + 분산 처리 필요
  → Redis 200MB → Redis 클러스터 또는 별도 인스턴스
  → 현 단계에서는 과도한 설계 → 필요 시 대응

→ 현재 규모(10,000 유저)에서는 단일 서버 배치 + Redis로 충분
→ 과도한 인프라 설계보다 "필요할 때 확장할 수 있는 구조"가 중요
```

## 9. 측정과 검증

### 9-1. 핵심 지표 (Key Metrics)

추천 시스템의 성공을 판단하는 지표:

```
[지표 1: 추천 전환율 (Recommendation Conversion Rate)]

정의: 추천된 질문 중 실제로 TodayQuestion으로 선택된 비율
공식: (추천 후 선택된 질문 수) / (노출된 추천 질문 수) × 100%

측정: recommendation_log에서 IMPRESSED → SELECTED 전환 추적
목표: 15% 이상 (기존 카테고리 브라우징 대비)

왜 이 지표인가:
  → 추천이 "적절했는가"의 가장 직접적인 증거
  → 전환율이 낮으면 추천 전략을 개선해야 함
```

```
[지표 2: 카테고리 다양성 변화]

정의: 추천 도입 전후, 유저당 평균 Diversity Score 변화
공식: AVG(Diversity Score) Before vs After

측정: 배치에서 유저별 Diversity Score를 이미 계산하므로 추적 가능
목표: 평균 Diversity Score 10% 이상 증가

왜 이 지표인가:
  → CoreDisc의 핵심 가치("자기 발견의 폭")에 직결
  → 추천이 실제로 사용자 행동을 변화시켰는지 증명
```

```
[지표 3: 질문 선택까지 소요 시간]

정의: 앱 접속 → 첫 번째 TodayQuestion 선택까지의 시간
측정: 클라이언트 측 이벤트 로깅 필요 (백엔드 단독으로는 측정 어려움)
목표: 평균 소요 시간 30% 이상 단축

왜 이 지표인가:
  → "선택 피로 감소"를 가장 직접적으로 측정
  → 추천이 없을 때: 브라우징 + 탐색 + 선택 = 느림
  → 추천이 있을 때: 추천 확인 + 선택 = 빠름
  → 단, 클라이언트 협업이 필요하므로 v1에서는 선택 사항
```

```
[지표 4: 전략별 전환율 비교]

정의: 4가지 전략 각각의 전환율
용도: 어떤 전략이 가장 효과적인지 판단 → 슬롯 배분 비율 조정

예상 가설:
  전략 1 (미답변 저장): 전환율 가장 높음 (이미 관심 확인)
  전략 2 (카테고리 확장): 전환율 중간 (새로운 시도 저항)
  전략 3 (Circle): 전환율 높음 (소셜 동기)
  전략 4 (몰입도): 전환율 가장 낮음 (개인화 약함)

→ 이 가설이 맞는지 데이터로 검증
→ 전환율이 높은 전략에 더 많은 슬롯 배분
```

### 9-2. 검증 방법

```
[단계 1: 오프라인 검증 (구현 전)]

기존 TodayQuestion 데이터로 시뮬레이션:
  → 유저 A의 과거 데이터에서 "추천했을 법한 질문" 생성
  → 유저 A가 실제로 선택한 질문과 비교
  → Hit Rate 측정: 추천 10개 중 실제 선택된 것이 포함되어 있는가?

이 검증의 의미:
  → 구현 전에 "이 전략이 의미가 있는가"를 데이터로 확인
  → Hit Rate가 랜덤 추천보다 높으면 유의미
  → 포트폴리오 스토리: "데이터 분석으로 전략의 유효성을 검증한 후 구현에 착수"
```

```
[단계 2: A/B 테스트 설계 (구현 후)]

A 그룹: 추천 API 노출
B 그룹: 기존 인기 질문만 노출 (대조군)

측정:
  - 질문 선택율 (선택 완료한 유저 비율)
  - 카테고리 다양성 점수 변화
  - 7일 리텐션 (7일 후 질문 선택 유지율)

유의점:
  → 실제 A/B 테스트를 돌리려면 클라이언트 협업 필요
  → 서버 단독으로는 "추천 API를 호출한 유저 vs 안 한 유저" 비교 가능
  → v1에서는 비교 분석이 핵심, 완전한 A/B 인프라는 v2 고려
```

## 10. 의사결정 기록

설계 과정에서 내린 주요 결정과 그 근거:

### 결정 1: ML 모델이 아닌 규칙 기반 추천을 선택한 이유

```
[선택지]
A. ML 모델 (Matrix Factorization, Neural CF 등)
B. 규칙 기반 (4가지 전략의 조합)

[선택: B]

근거:

① 데이터 규모의 현실
  → CoreDisc 유저 10,000명, 질문 풀 수천 개
  → ML 모델이 유의미한 패턴을 학습하기에 데이터가 부족
  → 과적합(overfitting) 위험이 높음

② 설명 가능성(Explainability)
  → "왜 이 질문을 추천했는가?"를 사용자에게 설명할 수 있어야 함
  → ML 모델: "모델이 추천했습니다" (블랙박스)
  → 규칙 기반: "친구가 답한 질문이에요" (투명)
  → CoreDisc의 "자기 발견" 맥락에서 추천 이유의 투명성은 중요

③ 유지보수성
  → ML 파이프라인: 모델 학습 인프라, 피처 스토어, 모델 서빙, 모니터링...
  → 규칙 기반: 기존 Spring Boot + Redis로 충분
  → 팀 규모와 인프라 현실에 맞는 선택

④ 점진적 발전 가능성
  → 규칙 기반으로 시작 → 데이터 쌓이면 ML로 전환 가능
  → recommendation_log가 미래 ML 학습 데이터가 됨
  → "지금 ML을 안 쓰는 것"이 아니라 "ML을 위한 기반을 만드는 것"

[포트폴리오 관점]
  "ML이 아닌 규칙 기반을 선택한 이유"를 설명할 수 있는 것 자체가 강점.
  "왜 이 기술을 안 썼는가"를 아는 것 = 기술 선택의 성숙도.
```

### 결정 2: 유사도 기반 협업 필터링을 v1에서 제외한 이유

```
[원래 고려했던 전략]
"나와 비슷한 질문을 고른 유저들이 추가로 고른 질문 추천"
→ 유저-질문 행렬 구성 → 코사인 유사도 → 추천

[제외 이유]

① 계산 비용
  → 유저 10,000명 × 유저 10,000명 유사도 행렬 = 1억 쌍
  → 매일 재계산하면 배치 시간 급증
  → 현 규모에서도 무거운데, 유저 증가 시 O(N²)로 폭발

② Circle이 이미 유사도의 프록시
  → 협업 필터링의 핵심: "나와 비슷한 사람"을 찾는 것
  → CoreDisc에서 Circle = "내가 이미 선별한 비슷한 사람"
  → 알고리즘이 유사한 사람을 찾는 것 vs 유저가 직접 골라놓은 것
  → 후자가 더 정확하고 계산 비용 0

③ v2에서 도입 가능
  → 데이터가 충분히 쌓이면 유사도 기반 추천 추가
  → 이때 recommendation_log 데이터가 학습에 활용됨
  → v1은 "기반 마련", v2는 "고도화"
```

### 결정 3: 추천 결과를 Redis에 저장하는 이유 (DB 테이블이 아닌)

```
[추천 결과의 특성]
  - 유효 기간: 24시간 (매일 새로 계산)
  - 용도: 읽기 전용 (API 응답에만 사용)
  - 정합성: 약간 오래된 데이터도 허용 (최신이 아니어도 됨)
  - 장애 시: 추천 없이 기존 탐색 경로로 폴백 가능

→ "24시간 후 자동 소멸하는 읽기 전용 데이터"
→ RDBMS보다 Redis TTL이 자연스러운 저장소

[만약 DB에 저장한다면]
  - 매일 전체 유저 DELETE + INSERT → 불필요한 쓰기 부하
  - 오래된 추천 수동 정리 필요 → 관리 포인트 추가
  - 추천 실패 시 오래된 데이터 노출 위험

→ Redis TTL = 데이터 생명주기가 저장소에 의해 자연스럽게 관리됨
```

### 결정 4: 추천 API를 별도 엔드포인트로 분리한 이유

```
[선택지]
A. 기존 GET /api/questions/selected 응답에 추천 포함
B. 별도 GET /api/questions/recommendations 엔드포인트

[선택: B]

근거:

① 관심사 분리
  → /selected: "내가 이미 고른 질문" (확정된 상태)
  → /recommendations: "시스템이 제안하는 질문" (탐색 상태)
  → 성격이 다른 데이터를 하나의 API에 섞으면 클라이언트 처리 복잡

② 호출 빈도가 다름
  → /selected: 매일 여러 번 호출 (답변 작성 시마다)
  → /recommendations: 질문 선택 화면에서만 호출 (하루 1~2번)
  → 캐싱 전략, 성능 요구사항이 다름

③ 점진적 도입
  → 별도 API이므로 클라이언트가 "추천 기능을 쓸지 말지" 선택 가능
  → 기존 기능에 영향 없이 추가 가능
```

## 11. 구현 단계 계획

### Phase 1: 데이터 검증 및 기반 구축

```
목표: 기존 데이터로 추천 전략의 유효성을 오프라인 검증하고,
      배치 인프라를 준비한다.

작업:
  1-1. TodayQuestion 데이터 분석
       → 유저별 카테고리 분포 현황 파악
       → 카테고리 편향도 측정
       → "같은 질문만 반복 선택하는 유저" 비율 확인

  1-2. 미답변 저장 질문 현황 분석
       → MemberOfficialQuestion - TodayQuestion 차집합 크기 확인
       → "저장했지만 안 쓴 질문"이 실제로 존재하는지

  1-3. 답변 길이 분포 분석
       → 질문별 평균 답변 길이 계산
       → 몰입도 점수의 분포가 의미 있게 차이가 나는지

  1-4. recommendation_log 테이블 생성
  1-5. 배치 Job 스켈레톤 구성 (기존 BatchScheduler에 추가)

산출물: 데이터 분석 리포트 + 테이블 + 배치 구조
```

### Phase 2: 배치 파이프라인 구현

```
목표: 전략 2(카테고리 확장)와 전략 4(몰입도)의 사전 계산 배치를 구현한다.

작업:
  2-1. 전략 2 배치 구현
       → 유저별 카테고리 분포 집계 쿼리
       → 미탐색/약탐색 카테고리 추출 로직
       → 추천 질문 선정 로직
       → Redis 저장 (rec:diversity:{userId})

  2-2. 전략 4 배치 구현
       → 질문별 몰입도 점수 집계 쿼리
       → Engagement Score 상위 질문 선정
       → Redis 저장 (rec:engagement)

  2-3. 배치 스케줄링
       → 기존 BatchScheduler에 추천 배치 추가
       → 매일 새벽 3시 실행 (기존 통계 배치 이후)

  2-4. 배치 모니터링
       → 처리 시간 로깅
       → 실패 시 알림 (기존 패턴 활용)

산출물: 동작하는 배치 + Redis에 사전 계산 결과 존재
```

### Phase 3: 실시간 추천 API 구현

```
목표: 4가지 전략을 조합하는 추천 API를 구현한다.

작업:
  3-1. 전략 1 (미답변 저장) 실시간 쿼리 구현
  3-2. 전략 3 (Circle) 실시간 쿼리 구현
  3-3. 추천 조합기 구현
       → 4가지 전략 결과 병합
       → 슬롯 배분 로직
       → 중복 제거 + 필터링
  3-4. API 엔드포인트 구현
       → GET /api/questions/recommendations
       → 응답 DTO 구성
  3-5. recommendation_log 기록 로직

산출물: 동작하는 추천 API
```

### Phase 4: 검증 및 측정

```
목표: 추천 시스템의 효과를 측정하고 포트폴리오 데이터를 수집한다.

작업:
  4-1. 부하 테스트
       → 추천 API 응답 시간 측정 (목표: 50ms 이내)
       → 배치 처리 시간 측정
       → Redis 메모리 사용량 확인

  4-2. 추천 품질 오프라인 검증
       → 과거 데이터 기반 Hit Rate 측정
       → 전략별 추천 결과 샘플 확인

  4-3. 지표 수집 체계 구축
       → recommendation_log 기반 전략별 전환율 조회 쿼리
       → Diversity Score 추이 추적

  4-4. 결과 문서화
       → Before/After 비교 데이터
       → 포트폴리오 스토리 작성

산출물: 성능 측정 결과 + 추천 품질 리포트
```

## 12. 리스크와 대응

### 리스크 1: Cold Start (신규 유저)

```
문제: 질문 선택 이력이 없는 유저에게는 전략 1, 2, 3이 모두 작동하지 않음

대응:
  → 전략 4(몰입도 기반)가 폴백 역할
  → 전체 유저 대상으로 계산된 "깊이 있는 질문"을 추천
  → 추가로 기존 인기 질문(Popular)을 보완으로 포함
  → 3~5일 활동 후 개인화 추천이 작동하기 시작

관점:
  → Cold Start는 모든 추천 시스템의 공통 문제
  → "해결했다"가 아니라 "인지하고 폴백을 설계했다"가 중요
```

### 리스크 2: 배치 실패

```
문제: 새벽 배치가 실패하면 Redis에 추천 데이터가 없음

대응:
  → Redis TTL을 25시간으로 설정 (배치 주기 + 여유 1시간)
  → 배치 실패 시 전날 데이터가 최대 1시간 더 유지됨
  → 전날 데이터도 만료되면 → 실시간 전략(1, 3)만으로 응답
  → 추천 데이터가 완전히 없으면 → 빈 배열 반환 (에러 아님)
  → 클라이언트는 추천이 없으면 기존 탐색 UI로 폴백

원칙:
  → 추천 시스템 장애가 서비스 전체 장애로 이어지면 안 됨
  → 추천은 "있으면 좋은 것", 없어도 기존 기능은 정상 작동
```

### 리스크 3: 추천 품질이 낮을 때

```
문제: 추천한 질문을 아무도 선택하지 않으면?

대응:
  → recommendation_log로 전략별 전환율 모니터링
  → 전환율이 특정 임계값 이하인 전략 → 슬롯 배분 축소
  → 전략 자체의 로직 조정 (예: 기간 변경, 가중치 조정)

관점:
  → "추천 품질이 완벽하다"가 아니라
  → "품질을 측정하고 개선할 수 있는 구조를 갖추었다"가 핵심
```

### 리스크 4: 개인정보/프라이버시

```
문제: Circle 친구의 질문 선택 이력을 추천에 활용 → 프라이버시 이슈?

대응:
  → 추천에 노출되는 것: "질문 내용" 뿐 (누가 골랐는지는 미노출 가능)
  → circleFriendCount만 표시 ("친구 2명이 답한 질문")
  → 개별 Circle 멤버 이름은 미노출
  → 질문 자체는 이미 공개된 질문 풀에 있는 것이므로 프라이버시 위험 낮음

추가 고려:
  → PERSONAL 타입 질문은 추천 대상에서 제외할 수 있음
  → 유저 설정으로 "내 질문 선택을 추천에 활용" 옵트아웃 제공 가능 (v2)
```

## 부록: 포트폴리오 스토리 요약

```
[한 줄 요약]
"매일 질문을 골라야 하는 소셜 다이어리에서,
 사용자 행동 데이터를 분석하여 4가지 추천 전략을 설계하고,
 하이브리드 파이프라인으로 50ms 이내 개인화 추천을 제공했다"

[스토리 흐름]

1. 문제 발견
   → 질문 선택이 서비스 DAU의 첫 번째 터치포인트인데,
     모든 탐색이 사용자 능동적 행동에 의존 → 선택 피로 → 이탈

2. 데이터 분석
   → 이미 존재하는 6가지 행동 데이터 식별
   → "저장했지만 답하지 않은 질문"이라는 핵심 인사이트 발견
   → Circle 관계가 취향 유사도의 자연스러운 프록시라는 발견

3. 전략 설계
   → 4가지 전략, 각각 다른 추천 목표
   → ML이 아닌 규칙 기반을 선택한 이유 (데이터 규모, 설명 가능성)
   → 협업 필터링을 v1에서 제외한 이유 (Circle이 더 정확한 프록시)

4. 아키텍처 설계
   → 하이브리드: 무거운 계산은 배치, 가벼운 조회는 실시간
   → Redis 캐싱으로 배치 결과 서빙
   → 기존 인프라(Redis, Caffeine, BatchScheduler) 활용 → 추가 비용 0

5. 측정 체계
   → recommendation_log로 전략별 전환율 추적
   → Diversity Score로 서비스 가치 달성 여부 측정
   → 오프라인 검증 → 온라인 A/B 테스트 단계적 접근

[면접 예상 질답]

Q: "왜 ML을 안 썼나요?"
A: "유저 만 명, 질문 수천 개 규모에서 ML 모델의 과적합 위험이 크고,
    추천 이유를 사용자에게 설명할 수 없습니다.
    규칙 기반으로 시작하고, recommendation_log로 ML 학습 데이터를 쌓아서
    규모가 커지면 전환하려는 계획입니다."

Q: "실제 효과는 어떻게 검증했나요?"
A: "과거 TodayQuestion 데이터로 오프라인 Hit Rate를 측정했고,
    recommendation_log로 전략별 전환율을 추적했습니다.
    전략 1(미답변 저장)의 전환율이 가장 높았고,
    전략 2(카테고리 확장) 도입 후 유저 평균 Diversity Score가 X% 증가했습니다."

Q: "Circle 추천이 아니라 일반 Follow 기반으로 하면 안 되나요?"
A: "Follow는 관계 강도를 모릅니다. 100명을 팔로우하면 너무 많은 질문이 나와
    노이즈가 됩니다. Circle은 유저가 직접 선별한 5~20명이므로,
    알고리즘이 유사도를 계산하는 것보다 더 정확한 관계 신호입니다.
    이것은 CoreDisc에 Circle이라는 관계 계층이 있기 때문에 가능한 전략입니다."
```
