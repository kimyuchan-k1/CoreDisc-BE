## 1. 출발점

### 1-1. Phase 1~6 성능 최적화 이후의 질문

6단계 성능 최적화를 통해 기존 병목을 해결했다:

```
피드 p95:     489ms → 246ms (-50%)
프로필 p95:   438ms → 127ms (-71%)
알림 p95:     439ms → 167ms (-62%)
처리량:       86 → 94 req/s (+9%)
```

최적화는 끝났지만, 한 가지 질문이 남았다:

> **"그래서 지금 이 구조가 몇 만 MAU에서 버틸 수 있는가?"**
> **"어디에서 먼저 터지는가?"**

이 질문에 답하려면 **현재 구조의 한계점을 먼저 측정**해야 한다.
최적화가 "기존 코드를 빠르게 만드는 것"이었다면, 이번은 **"구조적 한계를 찾아서 돌파하는 것"**이다.

### 1-2. 접근 방법

```
문제 발견 → 가설 수립 → 부하 테스트로 검증 → 해결책 구현 → 재측정으로 증명
```

기술 선택이 먼저가 아니다. **측정이 먼저다.**
"Redis를 써야 한다"가 아니라, "이 문제가 있고, 측정 결과 이 지점에서 터지고, 이 해결책이 가장 적합하다"는 흐름.

## 2. 현재 상태 진단

### 2-1. 코드에서 발견한 두 가지 구조적 문제

6단계 최적화 과정에서 코드를 깊이 분석하면서, 성능이 아닌 **정합성과 확장성** 관점에서 두 가지 구조적 위험을 발견했다.

#### 문제 A: 좋아요/댓글 카운트가 갱신되지 않는다

```java
// Post.java
@Column(name = "like_count")
@Builder.Default
private Integer likeCount = 0;    // 초기값 0, 이후 갱신 로직 없음

@Column(name = "comment_count")
@Builder.Default
private Integer commentCount = 0;  // 초기값 0, 이후 갱신 로직 없음
```

```java
// PostLikeCommandServiceImpl.createLike()
Post findPost = findAndValidatePost(request.postId());
// ... PostLike 엔티티 생성 및 저장
postLikeRepository.createPostLike(postLike);
// ← likeCount 증가 로직이 없다
```

```java
// CommentCommandServiceImpl.createComment()
Post post = postRepository.findById(postId);
Comment comment = Comment.create(post, member, request.content());
commentRepository.save(comment);
// ← commentCount 증가 로직이 없다
```

**현재 상태**: likeCount, commentCount는 항상 0이거나, 어딘가에서 COUNT 쿼리로 계산하고 있다.
어느 쪽이든, 카운트 정합성 메커니즘이 없다는 것이 핵심 문제다.

이 문제를 해결할 때, 단순히 `likeCount++`를 추가하면 **동시성 문제**가 발생한다.
이것이 Part A의 주제다.

#### 문제 B: 피드 쿼리가 팔로잉 수에 선형 비례한다

```java
// QueryPostRepositoryImpl.findPostFeed()
if (!followingIds.isEmpty()) {
    memberCondition.or(post.member.id.in(followingIds));
    // ↑ followingIds가 500개면 WHERE IN (500개 ID)
}
```

현재 피드 쿼리는 **Caffeine 캐시에서 followingIds를 가져와서 WHERE IN 절에 직접 전달**한다.
팔로잉 50명일 때와 500명일 때, 이 쿼리의 성능은 어떻게 달라지는가?

이것이 Part B의 주제다.

### 2-2. 두 문제의 관계

```
Part A (동시성):
  "100명이 동시에 같은 글에 좋아요를 누르면 카운트가 정확한가?"
  → 데이터 정합성 문제
  → 유저가 적어도 발생 가능 (인기 글 하나에 몰리면)

Part B (확장성):
  "팔로잉이 500명인 유저가 피드를 열면 몇 ms가 걸리는가?"
  → 쿼리 성능 문제
  → 유저 수와 관계 수가 늘어날수록 악화

공통점: 둘 다 "유저가 늘면 터지는" 문제
차이점: A는 동시 접근, B는 데이터 규모
```

## 3. Part A: 동시성 — 좋아요/댓글 카운트 정합성

### 3-1. 문제 정의

#### 현재 코드의 구조

좋아요 생성 흐름:

```
사용자 → POST /api/posts/{postId}/likes
  → PostLikeCommandServiceImpl.createLike()
    → Post 조회 (SELECT)
    → 중복 체크 (EXISTS)
    → PostLike 저장 (INSERT)
    → (likeCount 갱신 없음)
```

likeCount를 갱신하려면 어딘가에서 `post.likeCount += 1`을 해야 한다.
하지만 이것을 **어떻게** 하느냐에 따라 동시성 안전성이 결정된다.

#### Lost Update 문제

```
시간  스레드 A (유저 1의 좋아요)     스레드 B (유저 2의 좋아요)
─────────────────────────────────────────────────────────
T1   SELECT likeCount → 5
T2                                  SELECT likeCount → 5
T3   likeCount = 5 + 1 = 6
T4   UPDATE SET likeCount = 6
T5                                  likeCount = 5 + 1 = 6
T6                                  UPDATE SET likeCount = 6

결과: likeCount = 6 (기대값: 7)
→ 유저 2의 좋아요가 카운트에서 유실됨
```

이것이 Lost Update 문제다. JPA의 Dirty Checking 방식은 `SELECT → 수정 → UPDATE` 흐름을 타므로,
동시 접근 시 마지막 쓰기가 이전 쓰기를 덮어쓴다.

### 3-2. 가설

```
가설 1: "동시 좋아요 100건 시, JPA Dirty Checking 기반 카운트 증가는
         실제 좋아요 수보다 적은 값을 기록할 것이다."

가설 2: "동시성이 높을수록 (VU 수 증가) 유실률이 증가할 것이다."

가설 3: "DB 원자적 연산(UPDATE SET count = count + 1)으로 전환하면
         유실률이 0%가 될 것이다."
```

### 3-3. 측정 방법

```
[테스트 시나리오: 동시 좋아요 정합성 테스트]

사전 조건:
  - 특정 Post 1개 (postId = X)
  - likeCount = 0
  - 테스트 유저 100명 준비

테스트:
  - 100명의 유저가 동시에 같은 Post에 좋아요 요청
  - 모든 요청 완료 후:
    ① PostLike 테이블의 실제 레코드 수 조회 (SELECT COUNT)
    ② Post 테이블의 likeCount 값 조회
    ③ ① == ② 인지 확인

측정 항목:
  - 정합성: |실제 레코드 수 - likeCount| (0이면 정합)
  - 유실률: (실제 레코드 수 - likeCount) / 실제 레코드 수 × 100%
  - 에러률: 좋아요 요청 실패 비율 (UNIQUE 제약 조건 충돌 등)

반복:
  - VU 10명 → 50명 → 100명 → 200명으로 동시성 수준 변화
  - 각 수준에서 유실률 변화 추적
```

### 3-4. 해결 전략 비교

카운트 정합성을 보장하는 4가지 방법과 각각의 트레이드오프:

#### 전략 1: DB 원자적 연산 (UPDATE SET count = count + 1)

```sql
UPDATE post SET like_count = like_count + 1 WHERE id = ?
```

```java
// PostRepository에 추가
@Modifying
@Query("UPDATE Post p SET p.likeCount = p.likeCount + 1 WHERE p.id = :postId")
void incrementLikeCount(@Param("postId") Long postId);
```

```
장점:
  ✓ 구현이 가장 단순 (쿼리 1줄)
  ✓ DB가 원자성을 보장 → Lost Update 없음
  ✓ 기존 코드 변경 최소
  ✓ 추가 인프라 불필요

단점:
  ✗ 매 좋아요마다 Post 테이블 UPDATE 발생
  ✗ 동일 Post Row에 대한 경합 시 DB Row Lock 대기
  ✗ 인기 글에 초당 100개+ 좋아요 시 병목 가능성

적합한 규모: MAU 10만 이하 (대부분의 글에 동시 좋아요 10건 이내)
```

#### 전략 2: 비관적 락 (SELECT FOR UPDATE)

```java
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("SELECT p FROM Post p WHERE p.id = :postId")
Post findByIdForUpdate(@Param("postId") Long postId);
```

```
장점:
  ✓ 정합성 보장 (Lock으로 직렬화)
  ✓ JPA 엔티티의 likeCount를 직접 수정 가능

단점:
  ✗ Lock 대기 시간 발생 → 응답 지연
  ✗ 데드락 가능성 (여러 엔티티 동시 Lock 시)
  ✗ 인기 글에 대한 동시 요청이 직렬화됨 → 처리량 저하
  ✗ DB 커넥션을 Lock 기간 동안 점유

적합한 규모: 동시 경합이 낮은 환경
```

#### 전략 3: 낙관적 락 (@Version)

```java
// Post.java
@Version
private Long version;
```

```
장점:
  ✓ Lock 대기 없음 (충돌 시 예외 발생)
  ✓ 경합이 적을 때 성능 우수

단점:
  ✗ 충돌 시 OptimisticLockException → 재시도 로직 필요
  ✗ 인기 글에서 충돌률이 높으면 재시도가 반복 → 오히려 느려짐
  ✗ Post 엔티티에 version 컬럼 추가 필요 (기존 코드 영향)

적합한 규모: 경합이 가끔 발생하는 환경
```

#### 전략 4: Redis 원자적 카운터 + 주기적 DB 동기화

```
Redis: INCR post:{postId}:likeCount → 원자적 증가
스케줄러: 5분마다 Redis → DB로 동기화
```

```
장점:
  ✓ Redis INCR은 단일 스레드 → 완벽한 원자성
  ✓ DB 부하 없음 (실시간 UPDATE 없음)
  ✓ 초당 수천 건의 동시 좋아요도 처리 가능

단점:
  ✗ Redis 인프라 의존성 추가 (이미 있으므로 비용은 낮음)
  ✗ DB와 Redis 사이 최대 5분 정합성 차이 (Eventual Consistency)
  ✗ Redis 장애 시 카운트 유실 가능 → 복구 전략 필요
  ✗ 구현 복잡도 증가 (동기화 배치, 장애 복구)

적합한 규모: MAU 10만+ (인기 글에 초당 100건+ 좋아요)
```

### 3-5. 전략 선택: 단계적 접근

```
[Phase A-1] 먼저 문제를 측정한다
  → 카운트 갱신 로직 추가 (JPA Dirty Checking 방식)
  → 동시 좋아요 테스트 → 유실률 측정
  → "문제가 실제로 존재한다"를 수치로 증명

[Phase A-2] 가장 단순한 해결책부터 적용
  → DB 원자적 연산 (UPDATE SET count = count + 1)
  → 같은 테스트 재실행 → 유실률 0% 확인
  → 응답 시간 변화 측정

[Phase A-3] 원자적 연산의 한계점 측정
  → 동시 좋아요 수를 점진적으로 늘림 (100 → 500 → 1000)
  → Row Lock 대기로 인한 응답 지연이 임계점을 넘는 시점 측정
  → "DB 원자적 연산은 동시 좋아요 N건까지 유효하다"는 수치 도출

[Phase A-4] 필요 시 Redis 카운터로 전환
  → Phase A-3에서 한계점이 현실적으로 도달 가능한 수준이면
  → Redis 원자적 카운터 도입
  → 같은 테스트 재실행 → 한계점이 얼마나 확장되었는지 측정

이 단계적 접근의 의미:
  "Redis가 필요하다"고 미리 결정하는 게 아니라,
  "DB 원자적 연산으로 충분한지 측정하고,
   부족하면 Redis로 전환하는" 데이터 기반 의사결정.
```

### 3-6. 세부 구현 설계

#### Phase A-1: 카운트 갱신 로직 추가 + 문제 증명

```java
// PostLikeCommandServiceImpl.createLike() 수정
public void createLike(PostLikeRequestDTO request, Member member) {
    Post findPost = findAndValidatePost(request.postId());
    validateDuplicateLike(member, findPost);

    PostLike postLike = PostLike.create(findPost, member);
    postLikeRepository.createPostLike(postLike);

    // 카운트 증가 — JPA Dirty Checking 방식 (의도적으로 안전하지 않은 방식)
    findPost.incrementLikeCount();  // likeCount += 1
}
```

```java
// Post.java에 추가
public void incrementLikeCount() {
    this.likeCount += 1;  // NOT thread-safe — 이것을 증명하는 것이 목적
}
```

이 상태에서 동시성 테스트를 실행하여 **유실률을 측정**한다.
"안전하지 않다"를 알고 있지만, **수치로 증명하는 과정**이 포트폴리오의 핵심이다.

#### Phase A-2: DB 원자적 연산으로 전환

```java
// PostRepository (인터페이스)
void incrementLikeCount(Long postId);
void decrementLikeCount(Long postId);
void incrementCommentCount(Long postId);
void decrementCommentCount(Long postId);

// JpaPostRepository (구현)
@Modifying(clearAutomatically = true)
@Query("UPDATE Post p SET p.likeCount = p.likeCount + 1 WHERE p.id = :postId")
void incrementLikeCount(@Param("postId") Long postId);

@Modifying(clearAutomatically = true)
@Query("UPDATE Post p SET p.likeCount = p.likeCount - 1 WHERE p.id = :postId AND p.likeCount > 0")
void decrementLikeCount(@Param("postId") Long postId);
```

```java
// PostLikeCommandServiceImpl.createLike() 최종
public void createLike(PostLikeRequestDTO request, Member member) {
    Post findPost = findAndValidatePost(request.postId());
    validateDuplicateLike(member, findPost);

    PostLike postLike = PostLike.create(findPost, member);
    postLikeRepository.createPostLike(postLike);

    postRepository.incrementLikeCount(findPost.getId());  // DB 원자적 연산
}
```

```
왜 clearAutomatically = true인가:
  → @Modifying 쿼리는 영속성 컨텍스트를 우회하여 DB에 직접 실행
  → 영속성 컨텍스트에 캐시된 Post의 likeCount와 DB 값이 불일치
  → clearAutomatically = true로 영속성 컨텍스트를 초기화
  → 다음 조회 시 DB에서 최신 값을 읽음
```

#### Phase A-4: Redis 카운터 (필요 시)

```java
// RedisCounterService
@Service
public class RedisCounterService {

    private final StringRedisTemplate redisTemplate;

    // 원자적 증가
    public Long incrementLikeCount(Long postId) {
        String key = "post:" + postId + ":likeCount";
        return redisTemplate.opsForValue().increment(key);
    }

    // 원자적 감소
    public Long decrementLikeCount(Long postId) {
        String key = "post:" + postId + ":likeCount";
        return redisTemplate.opsForValue().decrement(key);
    }

    // 현재 값 조회
    public Long getLikeCount(Long postId) {
        String key = "post:" + postId + ":likeCount";
        String value = redisTemplate.opsForValue().get(key);
        return value != null ? Long.parseLong(value) : null;
    }
}
```

```java
// DB 동기화 배치 (5분마다)
@Scheduled(fixedRate = 300_000)
public void syncLikeCountsToDb() {
    Set<String> keys = redisTemplate.keys("post:*:likeCount");
    if (keys == null || keys.isEmpty()) return;

    for (String key : keys) {
        Long postId = extractPostId(key);
        String value = redisTemplate.opsForValue().get(key);
        if (value != null) {
            postRepository.updateLikeCount(postId, Long.parseLong(value));
        }
    }
}
```

```
Redis 카운터 도입 시 고려사항:

① 읽기 경로 변경
  → 피드에서 likeCount를 보여줄 때 DB가 아닌 Redis에서 조회
  → Redis MISS 시 DB 폴백 → Redis에 세팅

② Redis 장애 대응
  → Redis 장애 시 DB 원자적 연산으로 폴백
  → Redis 복구 후 DB 값으로 Redis 재세팅

③ 초기 데이터 세팅
  → 기존 PostLike 레코드를 COUNT하여 Redis에 세팅하는 마이그레이션 필요
  → SELECT post_id, COUNT(*) FROM post_like GROUP BY post_id

④ TTL 설정
  → 활성 글만 Redis에 유지 (7일 이내 활동이 있는 글)
  → 오래된 글은 Redis에서 만료 → 조회 시 DB 폴백 → 다시 캐싱
```

### 3-7. 댓글 카운트도 동일 적용

좋아요와 동일한 패턴:

```java
// CommentCommandServiceImpl.createComment() 수정
commentRepository.save(comment);
postRepository.incrementCommentCount(postId);  // DB 원자적 연산

// CommentCommandServiceImpl.deleteComment() 수정
comment.softDelete();
postRepository.decrementCommentCount(postId);  // DB 원자적 연산
```

댓글은 좋아요보다 동시성 경합이 낮으므로 (같은 글에 동시 댓글은 드묾),
DB 원자적 연산으로 충분할 가능성이 높다. 이것도 **측정으로 확인**한다.

## 4. Part B: 피드 확장성 — Pull 모델의 한계점은 어디인가

### 4-1. 문제 정의

현재 피드 쿼리의 구조:

```java
// PostQueryServiceImpl
List<Long> followingIds = followQueryService.getFollowingIds(member.getId());
List<Long> circleIds = followQueryService.getCircleFollowingIds(member.getId());

// QueryPostRepositoryImpl
// WHERE post.member.id IN (followingIds) — Caffeine 캐시에서 가져온 ID 목록
```

이 구조에서 **followingIds의 크기**가 쿼리 성능을 직접 좌우한다.

```
현재 테스트 환경:
  - 유저당 평균 팔로잉: ~50명 (시드 데이터 기준)
  - 피드 p95: 246ms

질문:
  - 팔로잉 100명이면? 200명? 500명? 1000명?
  - WHERE IN (1000개 ID)는 MySQL에서 어떻게 동작하는가?
  - 어느 시점에서 p95가 1초를 넘는가?
```

### 4-2. 가설

```
가설 1: "팔로잉 수가 증가하면 피드 쿼리 응답 시간이 선형 이상으로 증가할 것이다."
  → WHERE IN 절의 ID 수 증가 → 인덱스 스캔 범위 확대 → 응답 지연

가설 2: "팔로잉 500명 이상에서 피드 p95가 1초를 넘을 것이다."
  → MySQL의 WHERE IN 최적화 한계

가설 3: "동시 접속자(VU) 증가 시, DB 커넥션 풀이 먼저 병목이 될 것이다."
  → 피드 쿼리 1건당 DB 쿼리 7개 → 커넥션 점유 시간 증가

가설 4: "Caffeine 캐시 MISS 율이 높아지면 (유저 수 > 캐시 maxSize 5000)
         Follow 쿼리가 추가되어 성능이 급격히 저하될 것이다."
```

### 4-3. 측정 방법

### 4-4. 해결 전략 비교

#### 전략 1: 쿼리 최적화 (인프라 변경 없음)

```
접근: WHERE IN 절의 효율을 높이는 쿼리 구조 변경

방법 A: 서브쿼리 대체
  현재: WHERE post.member_id IN (1, 2, 3, ..., 500)  ← 애플리케이션에서 ID 전달
  변경: WHERE post.member_id IN (SELECT following_id FROM follow WHERE follower_id = ?)
  → DB 옵티마이저가 서브쿼리를 세미조인으로 최적화할 수 있음
  → 하지만 캐시를 활용하지 못함

방법 B: 팔로잉 ID를 임시 테이블로 전달
  → 대량 IN 절 대신 JOIN으로 변환
  → MySQL 8.0의 CTE(WITH) 활용 가능

방법 C: 팔로잉 ID를 청크로 분할
  → 500개를 100개씩 5번 쿼리 → UNION ALL
  → 쿼리 수 증가 vs IN 절 크기 감소 트레이드오프

예상 효과: 20~40% 개선 (추정, 측정 필요)
한계: 구조적 한계(Pull 모델)는 변하지 않음
```

#### 전략 2: Redis 피드 캐시 (핫 유저 한정)

```
접근: 피드 결과의 첫 페이지를 Redis에 캐싱

구조:
  키: feed:{userId}:{feedType}
  값: Redis Sorted Set (score = postId, member = postId)
  TTL: 5분

글 발행 시:
  → 작성자의 팔로워 목록 조회
  → 각 팔로워의 feed:{followerId}:ALL에 새 postId 추가
  → CIRCLE 글이면 circleIds에만 추가

피드 조회 시:
  ① Redis에서 feed:{userId}:{feedType} 조회 (ZREVRANGE)
  ② HIT → postIds로 Post 조회 (DB)
  ③ MISS → 기존 Pull 쿼리 실행 → 결과를 Redis에 캐싱

예상 효과: 피드 조회 시 DB 쿼리 7개 → 1개 (Post 조회만)
한계:
  → 글 발행 시 fan-out 비용 발생
  → 가시성(CIRCLE/PERSONAL) 변경 시 캐시 정합성 문제
  → 관계 변경 시 캐시 무효화 범위 결정 필요
```

#### 전략 3: 하이브리드 (Pull 유지 + 선택적 캐싱)

```
접근: 피드 쿼리 결과 자체를 캐싱하되, 가시성 검증은 유지

구조:
  키: feed_cache:{userId}:{feedType}:{page}
  값: 직렬화된 피드 응답 (JSON)
  TTL: 2분 (짧은 TTL로 정합성 보장)

피드 조회 시:
  ① Redis 캐시 확인
  ② HIT → 바로 반환 (2분 이내 데이터)
  ③ MISS → 기존 Pull 쿼리 → Redis에 저장

무효화:
  → 내가 글을 쓰면: 내 팔로워들의 캐시 삭제
  → 관계 변경 시: 관련 유저의 캐시 삭제
  → 2분 TTL로 최악의 경우에도 2분 후 갱신

예상 효과: 반복 피드 조회 시 DB 부하 0 (캐시 HIT)
한계:
  → 첫 조회(MISS)는 여전히 기존 쿼리
  → TTL 내에 관계 변경이 반영되지 않을 수 있음 (프라이버시 고려)
```

### 4-5. 전략 선택: 단계적 접근

```
[Phase B-1] 먼저 한계점을 측정한다
  → 팔로잉 수별, VU별 성능 측정
  → "현재 구조는 팔로잉 N명, VU M명까지 p95 < 500ms를 유지한다"
  → 한계점 수치 도출

[Phase B-2] 쿼리 최적화로 한계점 확장
  → WHERE IN 최적화, 쿼리 구조 개선
  → 같은 테스트 재실행
  → "쿼리 최적화 후 한계점이 N → N'으로 확장되었다"

[Phase B-3] 쿼리 최적화로 부족하면 캐싱 도입
  → Phase B-2의 한계점이 현실적 서비스 규모에 부족하면
  → Redis 피드 캐시 또는 하이브리드 캐싱 도입
  → 같은 테스트 재실행 → 한계점 재측정

이 단계적 접근의 의미:
  "처음부터 Redis 캐시를 설계"하는 게 아니라,
  "쿼리 최적화만으로 어디까지 가는지 확인하고,
   그래도 부족하면 캐싱을 도입"하는 공학적 판단.
```

```
  2-2. 동시성 테스트 재실행
       → 같은 조건에서 유실률 0% 확인
       → 응답 시간 변화 측정

  2-3. 동시성 스케일 테스트
       → 동시 좋아요 100 → 500 → 1000건
       → Row Lock 대기 시간 측정
       → "DB 원자적 연산은 동시 N건까지 p95 < 100ms"

  2-4. (조건부) Redis 카운터 도입
       → Phase 2-3에서 한계점이 서비스 규모에 부족하면
       → RedisCounterService 구현
       → 동기화 배치 구현
       → 같은 테스트 재실행

산출물:
  - Before: "유실률 X%"
  - After: "유실률 0%, p95 Xms"
  - "DB 원자적 연산은 동시 N건까지 유효 (Redis 필요 시점: M건)"
```

### Phase 3: Part B 해결 — 피드 확장성 개선 (3~5일)

```
작업:
  3-1. 쿼리 최적화 시도

산출물:
  - Before: "팔로잉 N명에서 p95 > 1초"
  - After: "팔로잉 N명에서 p95 < 500ms"
```

## 7. 의사결정 기록

### 결정 1: 왜 "먼저 측정"하는가 — 기술 선택 전에 문제 크기를 안다

```
[안티패턴]
  "좋아요 동시성 문제가 있을 수 있으니 Redis를 도입하자"
  → 문제의 크기를 모른 채 솔루션을 결정
  → Redis가 필요 없는 규모일 수도 있음
  → 오버 엔지니어링

[이 계획의 접근]
  "먼저 유실률을 측정하자. 그리고 DB 원자적 연산으로 해결되는지 확인하자.
   안 되면 그때 Redis를 고려하자."
  → 문제 크기에 맞는 솔루션 선택
  → "왜 이 기술을 썼는가"가 아니라 "왜 이 기술이면 충분한가"를 설명 가능

[포트폴리오 관점]
  면접관: "왜 Redis를 안 쓰고 DB 원자적 연산을 썼나요?"
  답변: "동시 좋아요 1000건까지 DB 원자적 연산으로 p95 < 50ms를 유지했습니다.
         현재 서비스 규모에서 초당 1000건의 동시 좋아요는 비현실적이므로
         DB 원자적 연산으로 충분합니다. Redis는 이 한계를 넘어설 때 도입합니다."

  이 답변이 "Redis를 도입했습니다"보다 성숙한 판단을 보여줌.
```

### 결정 2: 왜 비관적 락이 아닌 DB 원자적 연산을 먼저 시도하는가

```
비관적 락 (SELECT FOR UPDATE):
  → 트랜잭션 동안 Row Lock 유지
  → 다른 요청이 Lock 해제까지 대기
  → 좋아요처럼 빈번한 연산에는 병목

DB 원자적 연산 (UPDATE SET count = count + 1):
  → Row Lock이 UPDATE 실행 순간에만 잡힘 (밀리초 미만)
  → 대기 시간 최소
  → 별도 SELECT 없이 한 번의 UPDATE로 완료

→ "어떤 Lock 전략을 쓸 것인가"가 아니라
   "Lock 없이 해결할 수 있는 방법이 있는가"를 먼저 확인
```

### 결정 3: 왜 피드에 Push 모델을 바로 도입하지 않는가

```
Push 모델의 복잡도:
  → fan-out: 글 발행 시 모든 팔로워의 타임라인에 Push
  → 팔로워 1000명 → 1000번의 Redis 쓰기
  → 가시성 변경(Circle 해제) 시 소급 정리 필요
  → 운영 복잡도: 타임라인 크기 관리, Redis 메모리 관리

Pull 모델의 장점:
  → 항상 최신 데이터 (가시성 포함)
  → 구현/운영 단순
  → 현재 규모에서 충분한 성능

→ "Pull로 어디까지 갈 수 있는지"를 먼저 확인
→ 한계점 측정 결과에 따라 Push 필요 여부 결정
→ 이 결정의 근거가 "추측"이 아니라 "측정 결과"가 됨
```

### 결정 4: likeCount를 Post 테이블에 비정규화하는 이유

```
[선택지]
A. 매번 COUNT 쿼리: SELECT COUNT(*) FROM post_like WHERE post_id = ?
B. Post 테이블에 비정규화: post.like_count

[선택: B]

근거:
  ① 피드에서 매번 COUNT를 하면:
     → 피드 10개 글 × COUNT 2개 (좋아요 + 댓글) = 20개 추가 쿼리
     → N+1 문제 재발생 (Phase 2에서 해결한 것이 무의미해짐)

  ② 비정규화의 비용:
     → 쓰기 시 UPDATE 1회 추가 (원자적 연산)
     → 정합성 보장만 하면 됨

  ③ 읽기 >> 쓰기:
     → 피드 조회(읽기)는 초당 수백 건
     → 좋아요(쓰기)는 초당 수십 건
     → 읽기 최적화가 더 중요한 구조

  ④ 정합성 보장 방법:
     → DB 원자적 연산 (Phase A-2)
     → 필요 시 Redis 카운터 (Phase A-4)
     → 주기적 보정 배치 (COUNT와 likeCount 비교 → 불일치 시 보정)
```

## 8. 최종 목표 — 포트폴리오 성과 지표

### 8-1. Part A 기대 성과

```
[동시성 정합성]

Before:
  - likeCount 갱신 로직 없음 (카운트 미반영)
  - 갱신 로직 추가 시 동시 100건에서 유실률 X%

After:
  - DB 원자적 연산 도입 → 유실률 0%
  - 동시 좋아요 N건까지 p95 < 100ms
  - (Redis 전환 시) 동시 좋아요 M건까지 확장

핵심 수치:
  - 유실률: X% → 0%
  - 동시 처리 한계: N건 (DB) → M건 (Redis)
```

### 8-2. Part B 기대 성과

```
[피드 확장성]

Before:
  - 팔로잉 N명 이상에서 p95 > 1초
  - VU M명 이상에서 에러율 > 5%

After:
  - 쿼리 최적화 → 팔로잉 N'명까지 한계점 확장
  - (캐싱 도입 시) 팔로잉 수에 무관하게 p95 < 200ms
  - VU M'명까지 에러율 < 1%

핵심 수치:
  - 피드 한계: 팔로잉 N명 → N'명
  - 동시 접속 한계: VU M명 → M'명
  - MAU 추정: "현재 구조로 MAU X만까지 안정적"
```

### 8-3. 포트폴리오 스토리 요약

```
[한 줄 요약]
"서비스 확장성 한계를 공학적으로 측정하고,
 동시성 정합성과 피드 확장성 두 가지 병목을 발견하여
 단계적으로 해결한 과정"

[스토리 흐름]

1. 질문
   → "6단계 성능 최적화 후, 이 구조가 몇 만 MAU에서 버틸 수 있는가?"

2. 문제 발견
   → 코드 분석에서 두 가지 구조적 위험 발견
   → A: 좋아요/댓글 카운트에 동시성 보호가 없음
   → B: 피드 쿼리가 팔로잉 수에 선형 비례

3. 가설 수립 + 측정
   → A: "동시 좋아요 100건 시 유실률 X%일 것"
   → B: "팔로잉 500명 이상에서 p95 > 1초일 것"
   → k6 부하 테스트로 가설 검증

4. 단계적 해결
   → A: JPA Dirty Checking → DB 원자적 연산 → (필요 시 Redis)
   → B: 쿼리 최적화 → (필요 시 Redis 캐시)
   → 각 단계에서 "이것으로 충분한가?"를 측정하고 판단

5. 결과
   → A: 유실률 X% → 0%, 동시 처리 한계 N건
   → B: 피드 한계 팔로잉 N → N'명, 동시 접속 M → M'명
   → 통합: "MAU X만까지 안정적으로 서비스 가능"

[면접 예상 질답]

Q: "왜 처음부터 Redis를 안 쓰고 DB 원자적 연산부터 했나요?"
A: "동시 좋아요 1000건까지 DB 원자적 연산으로 p95 Xms를 유지했습니다.
    현재 규모에서 이 한계를 넘는 경우는 현실적으로 없으므로
    DB 원자적 연산으로 충분합니다.
    측정 없이 Redis를 도입했다면 불필요한 복잡도만 추가한 것이 됩니다."

Q: "Pull 모델의 한계를 어떻게 알았나요?"
A: "팔로잉 수를 50/100/200/500/1000으로 변화시키며 피드 p95를 측정했습니다.
    팔로잉 N명에서 p95가 1초를 넘었고, 이것은 WHERE IN 절의 크기에 비례하는
    MySQL의 인덱스 스캔 비용 때문이었습니다.
    쿼리 구조를 X로 변경하여 한계점을 N'명까지 확장했습니다."

Q: "카운트 정합성을 Redis로 관리하면 DB와 불일치하지 않나요?"
A: "최대 5분의 Eventual Consistency 차이가 있습니다.
    하지만 좋아요 카운트는 실시간 정확성보다 근사치가 중요한 데이터입니다.
    Instagram도 좋아요 수를 '좋아요 1,234개'가 아니라 '좋아요 약 1.2천 개'로
    보여주는 것처럼, 이 수준의 차이는 사용자 경험에 영향을 주지 않습니다.
    또한 5분마다 DB와 동기화하는 배치가 있으므로 장기적 정합성은 보장됩니다."
```
